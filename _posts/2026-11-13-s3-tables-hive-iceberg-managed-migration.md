데이터 레이크를 오래 운영한 조직이라면 “Apache Iceberg로 바꾸자”는 말보다 “운영 중인 Hive 테이블을 언제, 어떻게 끊지 않고 옮길 것인가”라는 질문이 더 어렵습니다. 수년 동안 쌓인 Parquet 파일, Glue Data Catalog의 테이블 정의, 배치·스트리밍 작업, Athena·Spark·Trino 쿼리가 서로 다른 전제 위에서 움직이기 때문입니다. 테이블 형식만 바꾸는 작업처럼 보여도 실제로는 스키마·파티션·파일 크기·권한·카탈로그·컷오버를 함께 조정해야 합니다.

AWS는 2026년 11월 4일 Amazon S3 Tables에 **AWS Glue에 등록된 Apache Hive 테이블을 관리형 Apache Iceberg 테이블로 이전하는 기능**을 공개했습니다. 소스는 같은 AWS 계정과 리전에 있는 Amazon S3의 Parquet 테이블이어야 합니다. S3 Tables는 마이그레이션 전 호환성 보고서를 만들고, 데이터 타입 변환·파일 재압축·작은 파일 합치기·검증을 수행하며, 운영 중인 소스에 쓰기를 계속하면서 여러 번 `sync`할 수 있게 합니다. 최종 `complete` 단계에서 짧은 컷오버를 거쳐 목적지 테이블을 읽기·쓰기가 가능한 상태로 전환합니다.

이 발표는 “버튼 한 번으로 모든 Hive가 Iceberg가 된다”는 뜻이 아닙니다. AWS가 반복적인 인프라와 변환 파이프라인을 관리해 주지만, 어떤 테이블을 옮길지, 쿼리 의미가 보존되는지, 늦게 도착한 데이터와 권한이 어떻게 처리되는지는 여전히 데이터팀의 설계입니다. Apache Iceberg 공식 문서가 설명하는 스키마 진화·숨은 파티셔닝·스냅샷·타임 트래블의 장점을 활용하려면, 마이그레이션을 **파일 복사 작업이 아니라 테이블 계약과 운영 절차의 전환**으로 봐야 합니다.

## 1. 11월 4일 발표에서 실제로 바뀐 것

### 직접 파이프라인을 만들던 구간이 관리형 작업이 됐다

기존에는 Hive 테이블을 Iceberg로 옮길 때 스키마를 읽고, 데이터를 다시 쓰고, 메타데이터를 만들고, 작은 파일을 정리하고, 실패한 작업을 재시도하는 파이프라인을 직접 구성해야 했습니다. Spark·EMR·Glue 작업이나 별도 오케스트레이터를 운영하면서 다음 질문에도 답해야 했습니다.

- 소스에 마이그레이션 중 새로 들어온 파일을 어떻게 따라잡을 것인가?
- Hive의 파티션 컬럼과 Iceberg의 파티션 스펙을 어떻게 매핑할 것인가?
- `INT96` 타임스탬프나 잘못된 타입을 어떻게 변환할 것인가?
- 일부 파일이 손상되거나 스키마가 섞였을 때 어디까지 롤백할 것인가?
- 목적지 테이블을 읽기 전용으로 두는 동안 어떤 쿼리가 어느 카탈로그를 보는가?

S3 Tables의 관리형 마이그레이션은 이 흐름을 `Start → Sync → Complete`라는 API 중심 단계로 노출합니다. 시작 시 소스 객체를 조사하고 호환성 보고서를 생성하며, 이후 변경분만 반복 동기화한 뒤 최종 전환을 수행합니다. AWS는 변환에 별도의 컴퓨팅 리소스를 프로비저닝할 필요가 없고, 데이터가 복사되는 양에 대해 비용을 지불하며 Hive-to-Iceberg 변환 자체에는 별도 요금이 없다고 설명합니다.

### 무엇이 지원되는가

출시 시점의 조건은 기능의 편리함만큼 중요합니다.

| 조건 | 출시 시 지원 범위 | 의미 |
| --- | --- | --- |
| 소스 형식 | Apache Hive 테이블 | Glue Data Catalog에 등록되어 있어야 함 |
| 파일 형식 | Apache Parquet | 비-Parquet 파일은 별도 변환 필요 |
| 위치 | Amazon S3 일반 버킷 | S3 Tables 목적지 버킷으로 복사 |
| 계정·리전 | 같은 AWS 계정·같은 리전 | 교차 계정·교차 리전은 별도 설계 |
| 목적지 | Amazon S3 Tables의 Iceberg 테이블 | 마이그레이션 중 읽기 전용 |
| 입력 변경 | 소스는 읽기·쓰기 계속 가능 | `sync`로 변경분을 반복 반영 |

따라서 “우리 데이터 레이크가 S3에 있다”만으로 바로 대상이 되는 것은 아닙니다. Hive 메타데이터가 Glue에 등록되어 있는지, 모든 객체가 Parquet인지, 계정·리전 경계가 조건에 맞는지 먼저 목록화해야 합니다.

## 2. 왜 Apache Iceberg로 옮기는가

Hive 테이블은 디렉터리와 파티션 이름을 테이블의 물리적 구조와 밀접하게 연결합니다. 날짜 파티션을 잘못 쓰거나 쿼리에서 물리 경로를 가정하면 결과가 틀리거나 불필요한 파일을 읽을 수 있습니다. Apache Iceberg는 데이터 파일과 테이블 메타데이터를 분리하고, 논리 스키마와 물리 레이아웃을 관리하는 오픈 테이블 형식입니다.

Apache Iceberg 공식 문서가 강조하는 기능은 다음과 같습니다.

| 기능 | Hive 중심 테이블에서의 문제 | Iceberg가 제공하는 방향 |
| --- | --- | --- |
| 스키마 진화 | 컬럼 위치·파티션 의존성이 변경을 어렵게 함 | 필드 ID 기반의 추가·삭제·이름 변경·타입 확장 |
| 숨은 파티셔닝 | 쿼리가 파티션 컬럼과 형식을 직접 알아야 함 | 논리 컬럼에서 파티션 값을 자동 유도 |
| 파티션 진화 | 레이아웃 변경이 새 테이블·쿼리 수정으로 이어짐 | 기존·새 파티션 스펙을 한 테이블에서 공존 |
| 타임 트래블 | 파일 경로 복사본에 의존 | 스냅샷 시점·버전 기준으로 재현 가능한 조회 |
| 원자적 커밋 | 파일 목록과 메타데이터를 함께 갱신하기 어려움 | 메타데이터 교체로 테이블 상태를 커밋 |
| 행 수준 삭제 | 불변 파일을 다시 쓰는 작업이 필요 | Iceberg v2의 delete file로 논리 삭제 표현 |

Iceberg의 장점은 특정 엔진의 독점 기능이 아니라 표준화된 메타데이터 계약에 있습니다. Spark, Trino, Flink, Hive, Impala, Athena 등 여러 엔진이 같은 테이블 상태를 읽을 수 있고, 물리 파일을 바꾸더라도 논리 쿼리를 덜 흔들 수 있습니다.

### 표준화와 관리형 스토리지는 다른 문제다

Iceberg 테이블 형식을 채택한다고 해서 파일 관리가 자동으로 끝나는 것은 아닙니다. 스냅샷 만료, 작은 파일 압축, 오래된 메타데이터 정리, 저장 클래스, KMS 키, 테이블 권한은 여전히 운영 대상입니다. S3 Tables는 이러한 유지보수 작업을 관리형 스토리지에 결합하지만, 조직은 비용·보존·감사 정책을 별도로 정의해야 합니다.

## 3. Start → Sync → Complete의 운영 의미

### 3.1 Start: 호환성 보고서가 첫 번째 산출물이다

마이그레이션을 시작하면 S3 Tables는 소스 객체를 조사하고 목적지 Iceberg 테이블을 생성합니다. AWS 설명에 따르면 변환 전에 호환성 보고서를 만들고, 지원되지 않는 타입·파일·메타데이터 문제를 확인합니다. 목적지 테이블은 마이그레이션 중 읽기 전용으로 유지됩니다.

이 보고서를 단순한 로그로 취급하면 안 됩니다. 다음 항목을 승인 문서로 남기는 편이 좋습니다.

- 대상 객체 수와 총 바이트, 누락·중복 객체
- 파티션별 파일 수와 가장 오래된·가장 새로운 데이터 시각
- Hive 타입과 Iceberg 타입의 변환 표
- `INT96`·타임존·소수점·NULL 처리 결과
- 손상 파일·스키마 불일치·지원되지 않는 압축 코덱
- 예상 압축·재작성량과 목적지 저장 비용
- 소스에 계속 들어오는 변경분을 `sync`로 따라잡을 수 있는지

호환성 보고서가 실패하거나 예상 밖 변환을 제시하면, 목적지 테이블을 만들었다는 이유만으로 다음 단계로 진행해서는 안 됩니다. 테이블별로 지원 여부를 판정하고, 지원 범위를 벗어난 데이터는 별도 파이프라인으로 분리해야 합니다.

### 3.2 Sync: 무중단은 쓰기 중단이 없다는 뜻이지 일관성이 자동 보장된다는 뜻이 아니다

소스 테이블은 마이그레이션 중에도 읽기·쓰기가 가능합니다. 최초 복사가 끝난 뒤 `sync-table-migration`을 여러 번 호출해 그 사이에 추가·변경된 데이터를 목적지에 반영할 수 있습니다. 이 구조는 장시간 복사 작업 동안 생산 시스템을 멈추지 않는 데 유리합니다.

하지만 `sync`가 모든 CDC 문제를 해결하지는 않습니다. 소스 쓰기 작업이 어떤 순서로 커밋되는지, 삭제가 파일·행 수준에서 어떻게 표현되는지, 늦게 도착한 이벤트가 어떤 파티션을 수정하는지 확인해야 합니다. “마지막 동기화가 끝났다”는 사실과 “목적지가 비즈니스 기준으로 소스와 동일하다”는 사실은 다릅니다.

권장하는 동기화 검증은 다음과 같습니다.

1. 소스와 목적지의 스냅샷 시각을 함께 기록한다.
2. 파티션별 행 수·바이트·최대 이벤트 시각을 비교한다.
3. 최근 변경분의 키 집합과 삭제 집합을 샘플링한다.
4. 소스에 새로 들어오는 쓰기를 계속 모니터링한다.
5. 동기화 지연이 허용 범위 안에 들어왔을 때만 컷오버 후보로 올린다.

### 3.3 Complete: 짧은 컷오버에도 계약 변경은 남는다

`Complete`는 목적지 테이블을 읽기·쓰기 가능한 상태로 승격하고 마이그레이션을 마무리하는 단계입니다. AWS는 소스 쓰기를 계속 허용하면서 최종 전환 시점에만 짧은 오프라인 구간을 둔다고 설명합니다. 그러나 쿼리 엔진이 새 카탈로그·새 테이블 ARN·새 권한을 바라보도록 바꾸는 작업은 남아 있습니다.

컷오버 시에는 데이터 외에도 다음을 전환해야 합니다.

- Athena·Spark·Trino·Flink 커넥터와 카탈로그 설정
- IAM·Lake Formation·S3 Tables 테이블 권한
- 대시보드·ETL·ML 피처 파이프라인의 테이블 식별자
- 파티션 컬럼을 직접 참조하던 쿼리
- 데이터 품질·신선도·비용 알림의 기준 경로
- 백업·보존·삭제·법적 보존 정책

따라서 컷오버는 “테이블 이름을 바꾸는 순간”이 아니라, **소스와 목적지의 읽기 계약·쓰기 계약·권한 계약을 함께 바꾸는 변경 관리 이벤트**입니다.

## 4. 마이그레이션 전후의 검증 체크리스트

### 데이터 정확성

- 전체 행 수와 파티션별 행 수가 허용 오차 안에 있는가?
- 합계·최소·최대·NULL 수·고유 키 수가 일치하는가?
- 금액·시간·소수점 타입 변환이 비즈니스 규칙을 보존하는가?
- 삭제·갱신·중복 이벤트가 목적지에 올바르게 반영됐는가?
- 압축·재작성 후 파일 통계가 쿼리 결과를 바꾸지 않는가?

### 쿼리 의미

- 날짜 필터와 파티션 프루닝이 같은 결과를 반환하는가?
- `SELECT *`와 명시적 컬럼 선택에서 컬럼 순서·이름이 달라지지 않는가?
- 조인 키가 타입 변환으로 문자열·숫자 혼합이 되지 않았는가?
- 타임 트래블·스냅샷 기준 조회가 감사 요구를 충족하는가?
- 구형 엔진이 Iceberg 버전·메타데이터 기능을 읽을 수 있는가?

### 운영·보안

- 목적지 테이블이 컷오버 전 읽기 전용으로 유지되는가?
- KMS 키·Lake Formation·IAM 권한이 소스와 같은 수준으로 적용되는가?
- 새로운 테이블 ARN과 리전이 로그·감사 정책에 반영됐는가?
- 실패한 `sync`를 재시작할 때 중복 복사나 부분 커밋이 생기지 않는가?
- 스냅샷 만료와 작은 파일 압축의 비용·보존 정책이 있는가?

### 성능·비용

- 대표 쿼리의 스캔 바이트와 지연시간이 개선 또는 허용 범위인가?
- 재압축·컴팩션으로 저장 비용이 줄었지만 CPU·요청 비용이 늘지 않았는가?
- S3 Intelligent-Tiering 객체가 의도하지 않은 액세스 계층으로 이동하지 않는가?
- 동기화 횟수와 컷오버 지연이 운영 비용을 과도하게 만들지 않는가?

## 5. 마이그레이션 전략을 세 가지로 나누기

모든 테이블을 같은 방식으로 옮기면 실패 확률이 높습니다. 데이터의 크기와 변경 속도, 쿼리의 중요도에 따라 전략을 분리해야 합니다.

| 전략 | 적합한 대상 | 장점 | 주의점 |
| --- | --- | --- | --- |
| 관리형 Start/Sync/Complete | Glue 등록 Parquet Hive 테이블, 같은 계정·리전 | 인프라·변환·동기화 부담 감소 | 지원 범위와 계정·리전 제약 |
| 자체 Spark/EMR 변환 | 복잡한 타입·교차 리전·맞춤 규칙 | 세밀한 변환·검증·오케스트레이션 | 운영·재시도·비용을 직접 관리 |
| 메타데이터 중심 전환 | 파일은 이미 Iceberg 호환, 메타데이터만 전환 | 데이터 재작성량을 줄일 수 있음 | 호환성과 엔진 동작을 직접 증명 |

AWS Prescriptive Guidance는 전체 데이터 파일을 다시 쓰는 방식과 메타데이터 레이어만 만드는 방식의 차이를 설명합니다. S3 Tables 관리형 기능은 호환성 검사와 파일 최적화를 포함한 관리형 데이터 복사 경로에 가깝기 때문에, 기존 파일과 메타데이터가 특정 조건을 만족한다고 해서 가장 비용이 낮은 선택이라고 단정하면 안 됩니다.

### 핵심 테이블부터 옮기지 말라

첫 번째 대상은 비즈니스 중요도가 높으면서도 복잡도가 낮은 테이블이 좋습니다. 예를 들어 읽기 중심의 일별 이벤트 테이블은 데이터 정확성·쿼리 패리티·비용을 검증하기 쉽습니다. 반대로 결제 원장, 실시간 CDC, 수천 개의 하위 파티션, 여러 리전에 복제되는 테이블은 초기 파일럿에서 제외하고 별도 런북을 만든 뒤 진행하는 편이 안전합니다.

## 6. Iceberg의 기능을 실제 운영에 연결하기

### 스키마 진화는 자유로운 변경이 아니다

Iceberg는 필드 ID를 사용해 컬럼 추가·삭제·이름 변경·타입 확장을 추적합니다. 이 기능은 Hive의 위치 기반 변경보다 안전하지만, 모든 변경을 무조건 허용한다는 뜻은 아닙니다. 숫자 타입 확장, 필수·선택 필드, 중첩 구조, 엔진별 지원 범위를 데이터 계약에 넣어야 합니다.

마이그레이션 뒤에는 다음 규칙을 권장합니다.

- 컬럼 이름 변경은 의미 변경과 분리해 리뷰한다.
- 삭제한 컬럼의 복구 기간과 스냅샷 보존 기간을 정한다.
- 생산 쿼리가 `SELECT *`에 의존하지 않게 한다.
- 스키마 변경을 데이터 품질 테스트와 카탈로그 이벤트에 연결한다.
- 구형 엔진이 새 필드 ID와 타입을 읽을 수 있는지 CI에서 검증한다.

### 숨은 파티셔닝은 쿼리 교육 방식도 바꾼다

Hive에서는 사용자가 `event_date=2026-11-13` 같은 파티션 경로를 알고 필터를 써야 빠른 조회가 가능했습니다. Iceberg는 논리 컬럼에서 파티션 변환을 유도하므로, 물리 파티션 이름을 쿼리에 하드코딩하지 않아도 파일 프루닝을 수행할 수 있습니다.

이는 개발자 경험을 개선하지만, 기존 쿼리를 그대로 옮겨도 동일한 성능이 보장된다는 뜻은 아닙니다. 날짜·타임존·변환 함수가 달라질 수 있고, 오래된 파일과 새 파티션 스펙이 공존하는 동안에는 여러 레이아웃을 함께 계획해야 합니다. 대표 쿼리의 실행 계획과 스캔 바이트를 컷오버 전후로 비교해야 합니다.

### 타임 트래블은 복구와 감사에 모두 쓰인다

Iceberg 스냅샷은 특정 시점의 테이블 상태를 재현하게 해 줍니다. 이는 잘못된 배치가 들어간 뒤 이전 버전으로 분석을 재실행하거나, 감사 시점의 데이터 상태를 증명하는 데 유용합니다. 하지만 스냅샷을 무기한 보존하면 메타데이터와 파일 비용이 늘고 개인정보 삭제 요구와 충돌할 수 있습니다.

따라서 스냅샷 정책에는 다음을 명시해야 합니다.

- 일반 분석용 최근 스냅샷 보존 기간
- 규제·감사용 장기 보존 테이블 또는 별도 아카이브
- 개인정보 삭제·법적 보존 요청이 들어왔을 때의 처리 경로
- `expire_snapshots`와 오래된 파일 삭제의 승인·감사 절차

## 7. AI 에이전트로 마이그레이션할 때의 경계

AWS 발표는 Kiro 같은 코딩 에이전트가 마이그레이션 계획 분석, IAM 정책 비교, Start·Sync·Complete API 호출, 진행 상태 모니터링을 단계별로 안내할 수 있는 Agent Toolkit 스킬도 소개합니다. 이 기능은 반복적인 CLI 작업을 줄여 주지만, 데이터 마이그레이션을 에이전트에게 무제한으로 맡겨도 된다는 뜻은 아닙니다.

에이전트가 해도 되는 일과 승인이 필요한 일을 분리해야 합니다.

| 에이전트에 허용할 수 있는 일 | 사람 승인 전에는 금지할 일 |
| --- | --- |
| Glue 테이블·객체 목록 수집 | 운영 테이블의 `Complete` 실행 |
| 호환성 보고서 요약 | 소스·목적지 쓰기 권한 변경 |
| 타입·파티션 변환 후보 제안 | 법적 보존·삭제 정책 변경 |
| 샘플 쿼리·데이터 품질 비교 생성 | 검증되지 않은 전체 재시도·롤백 |
| 비용·지연 추정 업데이트 | 계정·리전 경계를 넘는 복사 |

에이전트가 만든 마이그레이션 계획은 일반 코드 리뷰처럼 다뤄야 합니다. 입력 스키마, IAM 역할, 목적지 ARN, 예상 객체 범위, 동기화 시점, 롤백 절차를 사람이 확인한 뒤 실행 권한을 임시로 부여하는 방식이 적합합니다.

## 8. 교육·실무 실습 시나리오

실제 운영 데이터 대신 합성 Parquet 테이블과 Glue 카탈로그를 사용하면 마이그레이션의 핵심을 안전하게 검증할 수 있습니다.

1. 날짜·지역·고객 ID를 가진 작은 Hive 테이블을 만든다.
2. 의도적으로 작은 파일, `INT96` 타임스탬프, NULL, 늦은 이벤트를 섞는다.
3. S3 Tables의 `Start`를 실행하고 호환성 보고서를 분석한다.
4. 소스에 새 파티션과 삭제·갱신 이벤트를 추가한다.
5. `Sync`를 두 번 수행해 목적지가 변경분을 따라잡는지 확인한다.
6. 소스·목적지의 행 수·합계·고유 키·최대 이벤트 시각을 비교한다.
7. Athena·Spark에서 동일 쿼리의 결과·스캔 바이트·지연을 비교한다.
8. 컷오버 승인 후 `Complete`를 실행하고 읽기·쓰기 권한을 검증한다.
9. 잘못된 변환을 가정해 Iceberg 스냅샷으로 분석 상태를 재현한다.
10. 스냅샷 만료·작은 파일 압축·비용 알림을 설정한다.

평가의 핵심은 마이그레이션 명령이 성공했는지가 아닙니다. 학생 또는 담당자가 “어떤 데이터가 언제 복사됐고, 무엇을 근거로 컷오버했으며, 실패 시 어떤 상태로 돌아갈 수 있는가”를 설명할 수 있어야 합니다.

## 9. 발표의 한계와 도입 전 확인 사항

첫째, 관리형 기능의 출시 범위는 AWS Glue 등록·Parquet·동일 계정·동일 리전으로 제한됩니다. 다른 카탈로그, ORC·Avro 혼합 테이블, 교차 계정·교차 리전 데이터, 사용자 정의 변환 규칙은 별도 파이프라인이 필요할 수 있습니다. 기능이 지원된다고 해도 모든 Hive 기능과 쿼리 의미가 자동으로 보존되는 것은 아닙니다.

둘째, “생산 워크로드를 계속 실행할 수 있다”는 말은 소스 쓰기가 중단되지 않는다는 뜻입니다. 동기화 지연, 삭제 반영, 늦은 데이터, 중복 이벤트, 목적지 읽기 전용 상태를 운영 지표로 관리해야 합니다. 컷오버 직전에는 쓰기 지연을 줄이거나 승인된 일시 정지 구간을 두는 것이 필요할 수 있습니다.

셋째, 파일 재압축과 컴팩션은 저장 효율과 쿼리 성능을 높일 수 있지만, 데이터가 복사되고 다시 쓰이는 만큼 비용과 시간이 듭니다. “변환 수수료가 없다”와 “마이그레이션이 무료다”는 같은 말이 아닙니다. 복사 바이트, 요청, KMS, 로그, 장기 스냅샷, 쿼리 비용을 전체 수명주기로 계산해야 합니다.

넷째, Iceberg의 표준성이 곧 엔진 간 완전한 동작 일치를 보장하지는 않습니다. Iceberg 버전, 삭제 파일, 스냅샷, 파티션 변환, 시간 타입을 각 엔진이 어떻게 지원하는지 확인하고, 대표 쿼리를 실제 엔진으로 회귀 테스트해야 합니다.

다섯째, 목적지 테이블에 대한 권한이 소스와 자동으로 같아지지 않습니다. S3 Tables ARN·Lake Formation·KMS·카탈로그 권한을 새로 검토하고, 분석자·배치·ML 파이프라인의 최소 권한을 다시 부여해야 합니다.

## 결론: 마이그레이션의 핵심은 복사가 아니라 컷오버 계약이다

Amazon S3 Tables의 Hive-to-Iceberg 관리형 마이그레이션은 데이터 레이크 현대화의 반복 작업을 크게 줄일 수 있는 발표입니다. 호환성 보고서와 데이터 변환, 파일 최적화, 반복 동기화, 짧은 컷오버를 AWS가 관리해 주므로 팀이 Spark 작업과 재시도 인프라를 처음부터 만들 필요가 줄어듭니다. 특히 운영 중인 소스 테이블을 계속 읽고 쓰면서 목적지를 준비할 수 있다는 점은 빅뱅 전환의 부담을 낮춥니다.

그러나 Iceberg 전환의 가치는 `Complete` 버튼에서 자동으로 생기지 않습니다. 데이터 정확성·쿼리 의미·권한·비용·스냅샷 보존·롤백을 함께 검증해야 하고, 지원 범위를 벗어난 테이블은 관리형 기능과 자체 파이프라인을 조합해야 합니다. Apache Iceberg의 스키마 진화와 타임 트래블을 진짜 운영 자산으로 만들려면, 물리 파일을 옮기는 절차보다 테이블 계약과 데이터 품질 검증을 먼저 설계해야 합니다.

실무자가 가져갈 원칙은 간단합니다. **Start에서 범위를 증명하고, Sync에서 변경분을 검증하며, Complete는 데이터·쿼리·권한 계약이 모두 승인된 뒤 실행하라.** 이 순서를 지킬 때 S3 Tables의 관리형 편의성은 단순한 마이그레이션 자동화가 아니라, 운영 중인 데이터 레이크를 더 개방적이고 재현 가능한 테이블 플랫폼으로 바꾸는 기반이 됩니다.
