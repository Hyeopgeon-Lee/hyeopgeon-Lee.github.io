AI 에이전트가 한 번의 대화 안에서만 동작한다면 프롬프트 인젝션은 세션이 끝날 때 영향도 함께 사라질 수 있습니다. 그러나 에이전트가 사용자 취향, 업무 규칙, 과거 작업 결과를 장기 메모리에 저장하기 시작하면 공격자는 모델의 다음 답변이 아니라 **며칠 뒤 다른 세션의 판단**을 노릴 수 있습니다. 악성 문장이 기억으로 저장되고 자동으로 검색되어 다시 컨텍스트에 삽입되는 순간, 메모리는 편의 기능이 아니라 지속적인 공격면이 됩니다.

AWS는 2026년 11월 9일 AWS Security Blog에서 Amazon Bedrock AgentCore Memory의 메모리 포이즈닝(memory poisoning)에 대응하는 다층 쓰기 검증 패턴을 공개했습니다. 핵심은 메모리에서 의심스러운 항목을 나중에 찾는 데 그치지 않고, **영구 저장되기 전의 쓰기 경로를 통제점으로 삼는 것**입니다. AWS가 제시한 예시에서는 AgentCore Gateway 앞단의 Lambda 인터셉터가 네 가지 신호를 조합해 메모리 쓰기를 `ALLOW`, `QUARANTINE`, `DENY`로 분류합니다.

이 글은 AWS의 제품 사용법을 그대로 복사하는 튜토리얼이 아닙니다. 11월 9일 발표의 실제 범위를 구분하고, 11월 6일 공개된 MemoryDojo 연구와 Amazon Science의 환경 주입 공격 연구를 함께 읽어 메모리 보안의 기술적 의미를 분석합니다. 특히 의미 기반 점수의 한계, 격리 네임스페이스의 운영 조건, 검색·도구 호출 단계에서 추가로 필요한 통제를 교육과 실무 관점에서 정리합니다.

## 1. 메모리 포이즈닝은 “나쁜 답변”보다 오래 남는다

일반적인 프롬프트 인젝션은 현재 요청의 컨텍스트를 오염시킵니다. 사용자가 문서나 웹 페이지에 숨겨 둔 지시를 에이전트가 읽고, 그 세션에서 시스템 지시를 무시하거나 허가되지 않은 도구를 호출하게 만드는 식입니다. 메모리 포이즈닝은 그 다음 단계입니다. 공격자가 외부 콘텐츠나 대화를 통해 악성 지시를 장기 메모리에 남기면, 최초 공격을 본 사용자가 로그아웃한 뒤에도 영향이 이어질 수 있습니다.

전형적인 흐름은 다음과 같습니다.

| 단계 | 정상적으로 기대하는 동작 | 포이즈닝 시 발생하는 일 |
| --- | --- | --- |
| 세션 1 입력 | 사용자의 선호·업무 사실을 추출 | 공격자가 정상 문장 속에 장기 지시를 삽입 |
| 메모리 후보 생성 | 재사용할 가치가 있는 사실만 선택 | 악성 지시가 유용한 기억처럼 요약됨 |
| 영구 저장 | 사용자·테넌트 범위에 맞는 네임스페이스에 저장 | 공유 영역이나 다른 사용자 영역으로 확산 |
| 세션 2 검색 | 관련 사실을 참고해 답변 품질 향상 | 과거의 악성 지시가 새 시스템 지시처럼 주입 |
| 도구 실행 | 현재 사용자의 권한과 목표를 검증 | 데이터 유출·잘못된 거래·외부 전송으로 연결 |

AWS는 AgentCore Memory의 장기 메모리가 미래 대화에 자동으로 검색·주입될 수 있으므로, “무엇을 읽었는가”만큼 “무엇을 기억하게 허용했는가”가 중요하다고 설명합니다. 한 세션의 잘못된 쓰기가 여러 세션과 여러 에이전트에 영향을 줄 수 있는 이유입니다.

### 자동 검색은 편리하지만 신뢰를 부여한다

검색 증강 생성(RAG)이나 장기 메모리는 모델의 컨텍스트를 풍부하게 합니다. 하지만 검색된 텍스트가 사용자에게 보이지 않는 내부 프롬프트에 들어가면 모델은 그 내용을 현재 지시와 비슷한 수준의 신뢰도로 처리할 수 있습니다. “이 문장은 외부 문서에서 왔으니 신뢰하지 말라”는 메타데이터가 실제 추론 경계에서 강제되지 않으면, 메모리에 들어간 순간 악성 문장이 내부 사실처럼 승격됩니다.

따라서 메모리 항목마다 최소한 다음 속성을 보존해야 합니다.

- 누가 썼는가: 사용자·에이전트·도구·관리자
- 어떤 세션과 원본에서 추출됐는가: trace ID·문서 ID·메시지 해시
- 어느 범위에서 읽힐 수 있는가: 개인·팀·테넌트·전사
- 언제 검증·갱신·만료되는가: 생성 시각·재검토 시각·TTL
- 사실인가, 선호인가, 명령인가: 내용의 타입과 위험 등급

메모리를 단순한 문자열 배열로 저장하면 이후의 정책 판단과 사건 조사가 어려워집니다.

## 2. 11월 9일 AWS 발표에서 실제로 제공된 패턴

AWS 발표는 AgentCore Memory의 새로운 저장소를 소개한 것이 아니라, 기존 보안 계층을 메모리 쓰기 경로에서 조합하는 방법을 설명한 기술 패턴입니다. 게시글은 AgentCore Identity, Cedar 기반 AgentCore Policy, IAM 네임스페이스 조건 키, 메모리 전략의 통합 프롬프트, Bedrock Guardrails의 `ApplyGuardrail` API를 각각의 방어 계층으로 제시합니다.

| 계층 | 통제 대상 | 역할 |
| --- | --- | --- |
| Identity | 호출 주체 | 누가 에이전트와 메모리에 접근하는가 |
| IAM 조건 키 | `CreateEvent` 쓰기 경로 | 허용된 네임스페이스 변수와 리소스만 쓰기 |
| Cedar 정책 | 세밀한 권한·범위 | 개인·팀·공유 메모리의 결정적 경계 |
| 메모리 전략 프롬프트 | 요약·통합 결과 | 어떤 후보를 기억으로 추출할지 조정 |
| Guardrails API | 콘텐츠 정책 | 금지 주제·프롬프트 인젝션·민감정보 평가 |
| Lambda 인터셉터 | 쓰기 전 복합 판단 | 의미·패턴·경계·빈도를 합산해 격리·차단 |

AWS가 추가로 제안한 부분은 **쓰기가 실제 저장소에 도달하기 전** Gateway의 사전 Lambda 인터셉터에서 콘텐츠 인식 점수를 계산하는 것입니다. 기존 인터셉터가 도구 권한 검사나 요청 로깅을 이미 수행한다면, 같은 함수에 메모리 검증 모듈을 순차적으로 합칠 수 있다고 안내합니다.

### 결정은 세 가지뿐이지만, 점수는 확률이 아니다

게시글의 예시 파이프라인은 다음과 같은 구간을 사용합니다.

| 결정 | 예시 점수 구간 | 동작 |
| --- | --- | --- |
| `ALLOW` | 35 미만 | 대상 메모리 네임스페이스에 기록 |
| `QUARANTINE` | 35 이상 60 이하 | 격리 네임스페이스로 보내고 보안팀이 검토 |
| `DENY` | 60 초과 | 쓰기를 차단하고 SNS 알림 |

이 숫자는 공격 성공 확률이나 위험의 절대적 비율이 아닙니다. 네 가지 신호를 운영상 하나의 의사결정으로 묶기 위한 **정책 임계값**입니다. 고객 상담 에이전트와 소스 코드 변경 에이전트가 같은 임계값을 써야 한다는 뜻도 아닙니다. 공유 메모리와 고위험 도구를 사용하는 에이전트는 더 엄격한 경계를 적용하고, 개인 취향처럼 영향이 낮은 데이터는 관찰 모드에서 시작할 수 있습니다.

## 3. 네 가지 신호를 분해해서 보기

### 3.1 의미 드리프트: 대화와 기억 후보가 얼마나 멀리 떨어졌는가

AWS 예시는 현재 세션의 컨텍스트와 메모리 쓰기 후보를 임베딩으로 바꾸고 코사인 유사도를 비교합니다. 내용이 대화의 목표와 관계없이 갑자기 외부 송금, 시스템 지시, 비밀값 전송으로 바뀌면 의미 드리프트 점수를 높이는 방식입니다. 게시글은 Amazon Titan Text Embeddings V2를 사용해 비영어·난독화 표현도 정규식만으로 잡히지 않는 변형 신호로 보완할 수 있다고 설명합니다.

의미 드리프트가 유용한 이유는 공격자가 `ignore previous instructions` 같은 영어 표지를 쓰지 않아도 된다는 데 있습니다. 한국어·코드·우회 표현·간접적인 역할 부여도 현재 세션과 어울리지 않는다면 후보로 올릴 수 있습니다.

그러나 “대화와 멀다”가 곧 “악성”이라는 뜻은 아닙니다. 여행 상담 중 사용자가 다음 달 의료 예약을 선호사항으로 남기는 것처럼, 주제가 바뀌는 정상 업무도 존재합니다. 따라서 의미 점수 하나만으로 차단하면 정상 메모리의 다양성을 손상시킵니다. 테넌트별 업무 흐름을 반영한 기준선, 사용자 확인, 후속 검증이 필요합니다.

### 3.2 명령 패턴: 빠르고 싸지만 우회가 쉽다

정규식이나 문자열 패턴은 `이전 지시를 무시하라`, `이제부터 항상`, `너는 관리자다`처럼 지시형 문구를 빠르게 찾습니다. 지연과 비용이 낮고 조사자가 결과를 설명하기 쉽다는 장점이 있습니다.

반면 공격자는 표현을 바꾸거나 여러 문장에 나눠 쓰거나, 압축·인코딩·비유를 사용해 필터를 피할 수 있습니다. 정규식은 “알려진 형태의 위험 신호”이지, 문장의 의도를 이해하는 보안 판정기가 아닙니다. 의미 드리프트와 함께 사용하되, 패턴이 맞지 않았다는 이유로 안전하다고 결론 내리지 않아야 합니다.

### 3.3 네임스페이스 경계: 가장 결정적인 방어선

메모리 포이즈닝은 콘텐츠가 악성인지 판별하기 전에 **애초에 어디에 쓸 수 있는가**를 제한하면 피해를 크게 줄일 수 있습니다. 예를 들어 `user/{userId}/`는 개인 메모리, `shared/`는 엄격한 승인 대상, `system/`은 배포 파이프라인만 쓰기, `quarantine/`은 에이전트가 읽지 못하는 영역으로 나누는 방식입니다.

네임스페이스 검사는 의미 모델의 오판과 무관하게 작동해야 합니다. Lambda가 실패하거나 모델이 “나는 관리자다”라고 주장해도 Cedar와 IAM 조건 키가 다른 사용자의 영역을 차단해야 합니다. 특히 공유 영역에 한 번 들어간 기억은 여러 에이전트에 영향을 줄 수 있으므로, 개인 메모리보다 승인·감사·만료 조건을 강화해야 합니다.

### 3.4 쓰기 빈도 이상: 자동화 공격의 흔적

한 세션이 짧은 시간에 수십·수백 개의 기억을 생성한다면 정상적인 요약보다 자동화된 주입일 가능성이 커집니다. DynamoDB 카운터나 스트림으로 세션별 쓰기량을 기준선과 비교하고, 급증하면 보류·속도 제한·알림을 발생시키는 방식입니다.

빈도는 공격의 의미를 설명하지 못합니다. 긴 정상 작업을 수행하는 에이전트가 많은 이벤트를 기록할 수도 있고, 느린 공격자는 시간 간격을 늘려 탐지를 피할 수 있습니다. 따라서 빈도는 낮은 가중치의 보조 신호로 두고, 세션·사용자·네임스페이스별 기준선을 따로 유지하는 편이 안전합니다.

### 예시 가중치와 운영 해석

AWS 샘플 저장소는 의미 드리프트 40%, 명령 패턴 25%, 네임스페이스 경계 25%, 쓰기 빈도 이상 10%의 예시 가중치를 보여 줍니다. 이 비율은 “의미가 가장 중요하다”는 보편 법칙이 아니라, 샘플 파이프라인의 시작점입니다.

| 신호 | 예시 비중 | 잘 잡는 것 | 놓칠 수 있는 것 |
| --- | ---: | --- | --- |
| 의미 드리프트 | 40% | 주제와 동떨어진 지시, 비영어·난독화 표현 | 정상적인 업무 전환, 의미적으로 가까운 공격 |
| 명령 패턴 | 25% | 흔한 프롬프트 인젝션 문구 | 다국어·분할·인코딩 우회 |
| 네임스페이스 | 25% | 다른 사용자·시스템 영역 쓰기 | 올바른 영역에 저장된 악성 내용 |
| 쓰기 빈도 | 10% | 자동화된 대량 주입 | 저속 공격, 정상적인 장시간 작업 |

점수 계산은 설명 가능성을 위해 각 신호와 원본 근거를 함께 저장해야 합니다. “64점이어서 거부”만 남기면 오탐을 수정하거나 정책을 재학습하기 어렵습니다.

## 4. 왜 쓰기 시점 검증이 검색 시점 검증보다 먼저인가

메모리 보안은 저장 전·검색 후·도구 호출 전 세 곳에서 방어해야 합니다. 세 지점은 서로 대체 관계가 아닙니다.

1. **쓰기 전**: 악성·범위 밖·민감한 내용을 신뢰 저장소에 넣지 않는다.
2. **검색 후**: 오래된 규칙, 출처가 취소된 사실, 과거에 허용됐지만 현재는 위험한 내용을 컨텍스트에 넣기 전 재평가한다.
3. **도구 호출 전**: 메모리가 무엇을 말하든 현재 사용자·에이전트·리소스의 권한과 업무 계약을 다시 확인한다.

쓰기 전 검증은 오염된 메모리가 미래의 모든 세션으로 퍼지는 경로를 끊습니다. 검색 후 검증은 이미 존재하는 메모리의 신뢰도 변화와 모델 회수 오류를 다룹니다. 도구 호출 전 정책은 정상적으로 저장된 메모리라도 고위험 행동을 직접 승인하지 못하게 합니다.

AWS AgentCore 모범 사례 문서도 `CreateEvent` API에 입력 검증을 두고, 고객이 애플리케이션 개발·입력 검증·프롬프트 인젝션 방어를 책임져야 한다고 설명합니다. 클라우드 서비스가 메모리를 암호화해 주는 것과, 그 내용이 믿을 만한지 판단하는 것은 별개의 문제입니다.

### 권장 데이터 흐름

```text
외부 입력·도구 결과
        ↓
CreateEvent 입력 검증 + 민감정보 마스킹
        ↓
IAM/Cedar 네임스페이스 검사
        ↓
Guardrails + 명령 패턴 검사
        ↓
의미 드리프트·쓰기 빈도 계산
        ↓
ALLOW ─────→ 사용자/테넌트 메모리
QUARANTINE → 격리 저장소·사람 검토
DENY ──────→ 저장하지 않음·알림·사건 기록
        ↓
검색 시 재검증 → 도구 권한·업무 계약 검증
```

이 흐름에서 `QUARANTINE`은 단순히 “나중에 검토할 태그”가 아닙니다. 격리된 메모리를 에이전트의 기본 검색 대상에서 제외하고, 보안 분석자나 별도의 승인 프로세스만 읽을 수 있게 해야 합니다.

## 5. 최근 연구가 보여 주는 위험의 범위

### MemoryDojo: 모든 메모리 시스템이 같은 방식으로 취약하지 않다

2026년 11월 6일 공개된 *MemoryDojo* 연구는 네 가지 도메인, 155개의 다중 세션 장기 궤적과 다섯 종류의 메모리 시스템을 사용해 포이즈닝 정보의 삽입·지속·검색·행동 영향을 추적하는 벤치마크를 제안했습니다. 연구진은 메모리 시스템마다 하류 영향이 크게 달랐지만, 평가한 시스템 중 완전히 취약하지 않은 것은 없었다고 보고합니다.

이 결과가 중요한 이유는 “우리 메모리는 요약 모델이 다르니 안전하다”는 가정을 약화시키기 때문입니다. 메모리 시스템은 원문을 어떻게 요약하고, 어떤 항목을 우선 검색하고, 오래된 항목을 언제 잊는지에 따라 공격의 수명이 달라집니다. 따라서 제품 도입 전에는 단일 공격 문자열을 통과시키는지보다 **공격이 기억에 남고, 다른 세션으로 전파되고, 실제 도구 행동을 바꾸는지**를 측정해야 합니다.

### Amazon Science: 메모리 저장소에 직접 접근하지 않아도 오염될 수 있다

Amazon Science에 소개된 2026년 연구는 웹 에이전트가 오염된 상품 페이지 같은 외부 환경을 관찰하는 것만으로 장기 메모리가 오염될 수 있는 위협 모델을 제시합니다. 연구의 eTAMP 공격은 메모리 데이터베이스를 직접 쓰거나 관리자 권한을 탈취하지 않고도 한 사이트의 관찰을 미래의 다른 사이트 작업으로 이어지는 기억으로 만들 수 있다는 점을 강조합니다.

공개된 실험 수치는 특정 WebArena 환경과 연구 설정에서 얻은 결과이므로 일반 서비스의 공격 성공률로 해석하면 안 됩니다. 그러나 실무적 메시지는 분명합니다. **사용자가 직접 “이 내용을 기억해”라고 말하지 않아도, 브라우저·문서·메일·도구 결과가 메모리 쓰기 경로에 들어오면 동일한 검증이 필요하다**는 것입니다.

## 6. 운영 아키텍처에서 놓치기 쉬운 세부 사항

### 격리 네임스페이스는 읽기 권한까지 차단해야 한다

격리된 메모리를 별도 네임스페이스에 저장했지만 검색 인덱스가 모든 영역을 합쳐 버리면 격리는 형식에 그칩니다. 검색 서비스와 임베딩 인덱스에도 다음 조건을 적용해야 합니다.

- 일반 에이전트의 검색 필터에서 `quarantine/`를 제외한다.
- 보안 분석자만 원본·점수·근거를 조회할 수 있게 한다.
- 격리 항목을 재처리할 때 새 검증 ID와 승인자를 기록한다.
- 일정 기간 후 자동 삭제하거나 법적 보존 정책에 맞춰 별도 보관한다.
- 공유 메모리로 승격될 때 원본 출처와 검토 결과를 함께 복사한다.

### 메모리 타입별 TTL을 분리하라

사용자 선호는 오래 보관할 수 있지만, 현재 진행 중인 티켓 상태나 임시 승인 정보는 짧은 TTL이 적합합니다. 모든 메모리를 무기한 장기 기억으로 승격하면 포이즈닝의 지속 시간과 영향 범위가 함께 커집니다.

| 메모리 유형 | 권장 범위 | 추가 통제 |
| --- | --- | --- |
| 개인 선호 | 사용자 단위 | 사용자 확인·수정·삭제 기능 |
| 업무 사실 | 테넌트·프로젝트 단위 | 출처·갱신일·충돌 검증 |
| 시스템 정책 | 배포 파이프라인만 쓰기 | 코드 리뷰·서명·버전 롤백 |
| 도구 실행 결과 | 작업 단위·짧은 TTL | 결과 스키마·민감정보 마스킹 |
| 의심 내용 | 격리 전용 | 에이전트 읽기 금지·사람 승인 |

### 충돌을 숨기지 말고 보존하라

새 메모리가 기존 사실과 충돌할 때 최신 값으로 덮어쓰면 공격자가 정상 기록을 조용히 대체할 수 있습니다. 충돌을 별도 이벤트로 기록하고, 출처 신뢰도·작성자·승인자·시간을 비교한 뒤 정정 또는 보류하는 편이 좋습니다. “기억은 하나의 문자열”이 아니라 버전이 있는 주장(claim)으로 모델링해야 하는 이유입니다.

## 7. 샘플 구현을 운영에 가져올 때의 주의점

AWS가 연결한 `aws-samples/sample-agent-memory-poisoning-defense` 저장소는 CDK, Lambda, DynamoDB, SNS, Titan Embeddings V2, Cedar 정책과 테스트 페이로드를 포함한 교육용 샘플입니다. README에는 워밍 경로 지연 약 26ms, 프로비저닝된 동시성을 고려한 콜드 스타트 약 230ms, 하루 1만 회 쓰기에서 약 2.50달러라는 예시가 적혀 있습니다.

이 수치를 프로덕션 SLA나 AWS 공식 요금으로 인용해서는 안 됩니다. 리전, 모델 호출, 로그 보존, Lambda 메모리, DynamoDB 용량, SNS·KMS 사용량에 따라 달라지는 샘플 환경의 관측치입니다. 도입 전에 자신의 트래픽과 데이터 정책으로 다시 측정해야 합니다.

### 점수 엔진의 실패 모드를 정의하라

검증 Lambda나 임베딩 서비스가 타임아웃됐을 때 기본값이 `ALLOW`이면 공격자가 오류를 유도해 우회할 수 있습니다. 반대로 모든 실패를 `DENY`로 처리하면 일시적인 모델 장애가 사용자 업무를 멈출 수 있습니다. 위험도별로 다음과 같은 기본값을 분리하는 것이 현실적입니다.

| 상황 | 개인 선호 메모리 | 공유·시스템 메모리 |
| --- | --- | --- |
| 임베딩 타임아웃 | `QUARANTINE` 후 비동기 재검증 | `DENY` 또는 승인 대기 |
| Guardrails 오류 | 저장 보류·사용자 재시도 | 저장 금지·보안 알림 |
| DynamoDB 기준선 부재 | 낮은 가중치로 관찰 | 보수적 속도 제한 |
| 정책 버전 불일치 | 이전 정책으로 임시 평가 | 최신 정책 확인 전 차단 |

모든 결정에는 정책 버전, 신호별 원시 값, 예외 승인, 재처리 결과를 남겨야 합니다.

## 8. 테스트 시나리오: 악성 문장 하나로 끝내지 말기

메모리 방어 테스트는 문자열 필터 시험보다 긴 수명주기를 재현해야 합니다.

1. **정상 선호 저장**: “보고서는 항상 한국어로 요약해 줘”처럼 사용자의 선호를 저장한다.
2. **명령형 주입**: 이전 지시 무시, 시스템 역할 부여, 외부 전송 지시를 기억 후보로 만든다.
3. **지연 트리거**: “다음에 관리자라는 단어가 나오면…”처럼 미래 조건을 삽입한다.
4. **다국어·난독화**: 영어 키워드 없이 같은 의미를 표현하고 임베딩 탐지 결과를 비교한다.
5. **공유 영역 공격**: 개인 세션이 `shared/` 또는 `system/`에 쓰기를 시도한다.
6. **저속 분산 공격**: 여러 세션에 작은 조각을 나누어 써 빈도 탐지를 피한다.
7. **검색 전파**: 세션 2·3에서 해당 기억이 검색되는지, 출처 표시가 유지되는지 확인한다.
8. **도구 연결**: 포이즈닝된 기억이 실제 API·메일·브라우저 호출로 이어지는지 테스트한다.
9. **롤백**: 격리·삭제·재검증 후 다음 세션에서 기억이 정말 사라졌는지 확인한다.

공격성 테스트는 반드시 합성 계정과 비운영 도구를 사용해야 합니다. 목표는 공격을 성공시키는 것이 아니라, 실패하더라도 어떤 계층이 막았는지 증명하는 것입니다.

## 9. 교육 관점: “기억하는 에이전트”를 안전하게 가르치기

학생에게 메모리 포이즈닝을 설명할 때는 모델의 환각보다 데이터 수명주기를 먼저 보여 주는 것이 효과적입니다. 간단한 실습은 다음과 같습니다.

- 세션 1에서 정상 선호와 악성 지시가 섞인 문서를 에이전트에게 읽힌다.
- 쓰기 전 검증을 끄고 장기 메모리에 어떤 항목이 생성되는지 확인한다.
- 세션 2에서 다른 사용자가 정상 질문을 했을 때 악성 기억이 검색되는지 관찰한다.
- 네임스페이스 분리, 명령 패턴, 의미 드리프트, 쓰기 빈도 검증을 한 계층씩 켠다.
- `ALLOW`·`QUARANTINE`·`DENY` 결정과 근거를 대시보드로 비교한다.
- 마지막으로 포이즈닝된 기억이 도구 호출을 승인하지 못하도록 백엔드 권한 검증을 추가한다.

평가 기준은 답변이 자연스러운지가 아니라 다음 질문에 답하는 능력입니다.

- 이 기억은 누가, 언제, 어떤 원본으로 썼는가?
- 왜 신뢰 메모리와 격리 메모리를 구분했는가?
- 검색된 기억이 현재 사용자 권한을 확대하지 않는다는 것을 어디서 검증했는가?
- 정책·임베딩·검색 서비스가 실패했을 때 기본 동작은 무엇인가?
- 삭제와 롤백 후에도 인덱스·캐시·백업에 남은 복사본은 없는가?

## 10. 발표의 한계와 도입 전 체크리스트

첫째, AWS 게시글은 방어 패턴과 샘플 구현을 제안하는 기술 블로그입니다. `35`와 `60`이라는 임계값, 네 가지 가중치, SNS 알림 흐름이 모든 조직에 검증된 기준은 아닙니다. 자신의 정상 트래픽과 공격 시나리오로 재보정해야 합니다.

둘째, 임베딩 기반 의미 드리프트는 맥락을 이해하는 보조 신호이지 진실 판정기가 아닙니다. 정상적인 주제 전환을 오탐할 수 있고, 공격자가 정상 대화와 의미적으로 가까운 문장을 만들면 점수가 낮아질 수 있습니다. 생성형 모델의 판단을 추가하더라도 그 결과를 결정적 권한으로 사용해서는 안 됩니다.

셋째, 검증을 통과한 메모리도 시간이 지나면 틀릴 수 있습니다. 직원 이동, 정책 변경, 서비스 종료, 권한 회수는 기존 기억의 유효성을 바꿉니다. TTL·재검토·출처 폐기 이벤트를 메모리 검색 정책과 연결해야 합니다.

넷째, 메모리 방어는 AgentCore Gateway 안에서 끝나지 않습니다. 브라우저·메일·문서·MCP 도구·벡터 저장소·캐시·백업 등 모든 쓰기 경로가 같은 정책을 우회하지 않는지 확인해야 합니다. AWS의 공유 책임 모델처럼 클라우드 인프라 보호와 애플리케이션 입력 검증은 다른 책임입니다.

도입 전에 다음을 확인하면 좋습니다.

- 모든 메모리 쓰기가 하나의 검증 경로를 거치는가?
- 사용자·테넌트·시스템·격리 네임스페이스가 IAM과 검색 필터에서 일관되게 분리되는가?
- 메모리 항목에 원본·작성자·출처·TTL·정책 버전이 있는가?
- `QUARANTINE` 항목을 에이전트와 일반 검색 인덱스가 읽지 못하는가?
- 점수 엔진 장애 시 위험도별 보수적 기본값이 정의돼 있는가?
- 검색 후와 도구 호출 전에도 권한·출력·업무 계약을 재검증하는가?
- 공격 성공이 아니라 삽입·지속·전파·행동 변화까지 측정하는가?
- 샘플 코드의 비용·지연·임계값을 자체 부하와 규제 요구에 맞게 검증했는가?

## 결론: 에이전트의 기억은 데이터베이스이자 실행 경계다

Bedrock AgentCore Memory의 메모리 포이즈닝 대응 발표가 주는 가장 중요한 메시지는 “더 좋은 프롬프트를 쓰자”가 아닙니다. 에이전트가 기억을 저장하는 순간, 그 쓰기 경로는 데이터베이스 입력 검증과 권한 경계가 동시에 필요한 보안 인터페이스가 된다는 점입니다.

AWS가 제시한 Lambda 인터셉터와 `ALLOW`·`QUARANTINE`·`DENY` 흐름은 기존 IAM·Cedar·Guardrails를 대체하지 않고 보완합니다. 의미 드리프트는 새로운 표현을 찾는 데 도움을 주지만 오탐과 우회가 있고, 정규식은 빠르지만 제한적이며, 네임스페이스 정책은 콘텐츠를 이해하지 못해도 가장 확실한 범위 경계를 제공합니다. 네 신호를 합산하더라도 검색 후 검증과 도구 호출 권한 검사는 여전히 필요합니다.

실무자가 가져갈 원칙은 간단합니다. **기억하기 전에 검증하고, 검색할 때 출처를 표시하며, 행동하기 전에 권한을 다시 확인하라.** 메모리의 삽입·지속·전파·행동 변화를 한 사건의 시간선으로 측정할 때, 개인화 기능은 비로소 통제 가능한 에이전트 운영 자산이 됩니다.
