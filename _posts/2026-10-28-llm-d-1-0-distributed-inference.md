LLM을 한 번 호출해 답을 받는 서비스와, 여러 번의 추론·도구 호출을 반복하는 에이전트 서비스는 인프라 관점에서 전혀 다른 문제를 만듭니다. 에이전트는 같은 시스템 프롬프트와 문서, 코드베이스를 여러 턴에 걸쳐 다시 사용합니다. 요청이 갑자기 몰리면 한 사용자의 긴 작업이 다른 사용자의 첫 토큰 지연을 길게 만들기도 합니다. 단순한 라운드로빈 로드밸런서와 GPU 서버 수를 늘리는 것만으로는 이 패턴을 효율적으로 처리하기 어렵습니다.

2026년 10월 20일, llm-d 프로젝트는 **llm-d 1.0**을 공개했습니다. llm-d는 vLLM과 SGLang 같은 모델 서버를 Kubernetes 위에서 연결해, 요청을 어느 복제본으로 보낼지와 캐시를 어디에 둘지, 프리필과 디코드 자원을 어떻게 나눌지를 조정하는 오픈소스 분산 추론 계층입니다. 이번 1.0은 단일 성능 기법의 실험판을 넘어 멀티테넌트 품질 보장(QoS), 라우터 고가용성, 프리필·디코드의 무중단 롤링 업데이트, 에이전트 세션 인식 라우팅을 안정적인 v1 API와 함께 묶었다는 점이 핵심입니다.

이 글은 [llm-d 공식 1.0 발표](https://llm-d.ai/blog/llm-d-v1.0-state-of-the-art-inference-ready-for-day-2), [Google Cloud 기술 설명](https://cloud.google.com/blog/topics/ai-infrastructure/llm-d-1-0-an-open-source-stack-for-distributed-inference), [IBM Research의 운영 관점 분석](https://research.ibm.com/blog/llmd-1-0-is-ready-for-production-inference-serving), [IBM·Red Hat 공동 보도자료](https://newsroom.ibm.com/2026-10-20-llm-d-1-0-advances-open%2C-cost-efficient-ai-inference-for-production-scale), 그리고 독립 분석기관 NAND Research의 기술 정리(2026년 10월 21일)를 교차 확인해 작성했습니다. 벤더와 프로젝트가 제시한 처리량·비용 수치는 특정 모델, 하드웨어, 트래픽 패턴에서 얻은 결과이므로 우리 서비스의 SLA나 비용으로 바로 환산해서는 안 됩니다.

## 1. 1.0이 해결하려는 문제는 “모델 서버 한 대”가 아니다

기존 추론 구조는 보통 다음과 같습니다.

1. API 게이트웨이가 요청을 받습니다.
2. 로드밸런서가 여러 vLLM 또는 SGLang 복제본 중 하나를 고릅니다.
3. 선택된 서버가 프롬프트를 읽는 프리필(prefill)과 토큰을 생성하는 디코드(decode)를 모두 수행합니다.
4. 서버의 GPU 메모리에 KV 캐시가 남아 있으면 다음 요청이 재사용하지만, 다른 복제본으로 이동하면 같은 프롬프트를 다시 계산합니다.

짧은 단발성 질의에서는 이 구조도 충분할 수 있습니다. 그러나 에이전트는 한 작업에서 수십 번 모델을 호출하고, 각 호출이 앞선 결과와 긴 문맥을 공유합니다. 라운드로빈이 매번 다른 GPU를 고르면 캐시 적중률이 내려가고 입력 토큰을 반복 계산하게 됩니다. 긴 문맥이 GPU 메모리를 채우면 유용한 캐시가 쫓겨나고, 새 요청을 처리하기 위한 모델 서버의 대기열도 길어집니다.

llm-d는 모델 자체를 바꾸는 프레임워크가 아니라 **모델 서버들의 집합을 하나의 조정된 추론 풀로 만드는 계층**입니다. 라우터가 캐시와 부하 상태를 보고 복제본을 고르고, 캐시가 GPU에 모두 들어가지 않으면 CPU 메모리나 저장소로 옮기며, 프리필과 디코드가 서로 자원을 빼앗지 않도록 별도의 풀로 운영할 수 있게 합니다.

## 2. 무엇이 새롭고, 무엇이 기존 기능인가

llm-d 1.0의 의미를 정확히 보려면 “이번에 처음 등장한 기능”과 “기존 기능을 운영 가능한 형태로 통합한 부분”을 나눠야 합니다.

| 영역 | llm-d가 제공하는 방식 | 1.0에서의 의미 |
| --- | --- | --- |
| 라우팅 | 프리픽스 캐시와 부하를 함께 고려해 모델 서버 선택 | 세션·턴 우선순위와 결합해 에이전트 요청을 처리 |
| KV 캐시 | GPU HBM, CPU 메모리, SSD·원격 파일시스템으로 계층형 오프로딩 | 긴 문맥의 재계산과 메모리 압박을 완화 |
| 실행 분리 | 프리필과 디코드 복제본을 별도 풀로 구성 | DisaggregatedSet으로 두 풀의 버전·준비 상태를 함께 관리 |
| 트래픽 제어 | 우선순위·공정성 기반 flow control | 한 테넌트의 폭주가 다른 테넌트의 SLO를 침해하지 않게 함 |
| 운영 | 라우터 hot standby, 안정화된 v1 구성 API | 장애·점진적 배포·롤백을 서비스 중단 없이 수행 |
| 모델 서버 | vLLM, SGLang 등과 연동 | 특정 엔진·가속기에 종속되지 않는 공통 제어면 지향 |

IBM Research가 설명하듯 프리픽스 캐시 인식 라우팅, KV 캐시 오프로딩, 배치 최적화, 프리필·디코드 분리, 대규모 전문가 병렬화 자체는 1.0 이전에도 개발돼 왔습니다. 1.0의 변화는 이 기법들이 서로 충돌하지 않도록 요청 경로와 운영 절차를 함께 다듬은 데 있습니다. 성능 데모와 매일 업그레이드·장애조치·테넌트 경쟁을 견디는 서비스 사이의 간극을 줄인 셈입니다.

## 3. 에이전트에게 중요한 것은 “세션을 기억하는 라우터”다

에이전트의 각 턴을 독립 요청으로 취급하면 같은 문맥을 다시 읽게 됩니다. llm-d 1.0은 세션 상태와 캐시 위치를 라우터가 참고하도록 합니다.

- **세션 인식 라우팅**: 이전 턴의 KV 캐시를 가진 복제본으로 후속 요청을 보냅니다.
- **포화 시 재분배**: 캐시 지역성을 우선하되 복제본이 가득 차면 다른 서버로 이동해 전체 용량을 지킵니다.
- **턴 우선순위**: 진행 중인 에이전트 루프의 다음 턴을 일반 신규 요청과 구분해 지연을 관리합니다.
- **Responses API 상태**: `previous_response_id` 같은 상태를 이용해 애플리케이션이 긴 대화 이력을 매번 다시 보내지 않도록 합니다.

이 동작은 단순히 네트워크 홉을 하나 줄이는 최적화가 아닙니다. 입력 토큰을 다시 프리필하는 GPU 시간을 줄이고, GPU 메모리에 이미 계산된 상태를 재사용해 첫 토큰 시간(TTFT)을 낮추는 방법입니다. Google Cloud는 Ironwood TPU(주장상 TPU 7x) 기반 에이전트 코딩 워크로드에서 프리픽스 인식 라우팅과 호스트 메모리 오프로딩을 함께 사용했을 때 일반 Kubernetes Service 대비 중앙값 TTFT가 85% 이상 줄고 총 처리량이 2.4배가 됐다고 보고했습니다. 이 수치는 해당 TPU·모델·트래픽 조건의 결과이며, 짧은 프롬프트나 캐시 공유가 거의 없는 서비스에서는 같은 효과가 나오지 않을 수 있습니다.

## 4. KV 캐시를 “GPU 밖으로 내보내는” 이유

트랜스포머 추론에서 KV 캐시는 이미 읽은 토큰의 중간 상태입니다. 캐시가 남아 있으면 다음 턴에서 긴 프롬프트의 앞부분을 다시 계산하지 않아도 됩니다. 문제는 캐시가 GPU HBM을 계속 차지한다는 점입니다.

llm-d는 다음과 같은 계층을 조합합니다.

1. GPU HBM: 가장 빠르지만 용량이 작습니다.
2. 호스트 CPU 메모리: 지연은 늘지만 더 많은 캐시를 보관할 수 있습니다.
3. SSD 또는 원격 파일시스템: 용량은 크지만 네트워크·스토리지 지연을 감수해야 합니다.

vLLM의 OffloadingConnector, LMCache, SGLang의 HiCache와 같은 구성요소가 이 이동을 담당합니다. Google Cloud는 Managed Lustre를 포함한 다중 계층 오프로딩이 5만 토큰 프롬프트에서 CPU 메모리만 사용하는 경우보다 TTFT를 약 40% 개선하고 종단 간 지연을 30% 줄였으며 GPU 시간 요구량을 거의 60% 낮췄다고 소개했습니다. 이러한 숫자는 A3 Mega 클러스터와 특정 70B 모델의 공개 벤치마크에 기반합니다.

오프로딩은 공짜가 아닙니다. 캐시 블록을 옮기는 네트워크 대역폭과 저장소 I/O가 필요하고, 원격 캐시가 최신 상태인지 확인해야 합니다. 캐시 적중률이 낮은 서비스라면 GPU에서 계산하는 편이 오히려 빠를 수 있습니다. 따라서 도입 전에는 프롬프트 공통 접두사의 비율, 캐시 재사용 간격, GPU·CPU·스토리지 간 전송량을 함께 측정해야 합니다.

## 5. 프리필·디코드 분리는 성능과 운영을 동시에 바꾼다

프리필은 긴 입력을 읽는 계산 집약적인 단계이고, 디코드는 한 토큰씩 생성하며 메모리 대역폭의 영향을 크게 받는 단계입니다. 두 단계를 같은 복제본에서 처리하면 긴 문서 프리필이 대화형 디코드 요청을 밀어낼 수 있습니다.

llm-d는 프리필, 디코드, 멀티모달 인코딩을 각각의 풀로 나누고, 두 풀 사이에 KV 캐시를 이동할 수 있게 합니다. 그러면 다음과 같은 조정이 가능해집니다.

- 긴 문서·배치 작업이 많을 때 프리필 풀만 확장
- 대화형 사용자 요청이 많을 때 디코드 풀을 확장
- 대규모 MoE 모델의 전문가 병렬화를 여러 노드에 배치
- 새 버전을 배포할 때 프리필·디코드가 호환되는 쌍으로 준비된 뒤 트래픽 전환

1.0의 DisaggregatedSet은 프리필과 디코드 복제본을 하나의 논리 단위로 관리합니다. 한쪽만 새 버전이 된 상태로 요청이 들어가 KV 형식이나 모델 가중치가 어긋나는 사고를 줄이는 장치입니다. 다만 분리된 풀은 네트워크와 운영 구성요소를 더 추가합니다. 노드 간 연결 지연, KV 전송 실패, 두 풀의 용량 불균형을 관찰할 수 없다면 단일 서버보다 문제를 찾기 어려워집니다.

## 6. 멀티테넌트 QoS는 “가장 비싼 요청부터 처리”가 아니다

AI 플랫폼에는 서로 다른 요청이 섞입니다.

- 사용자가 기다리는 대화형 질의
- 백그라운드 문서 요약
- 에이전트의 반복적인 도구 호출
- 학습·평가용 배치와 RL 롤아웃

모든 요청을 같은 큐에 넣으면, 짧은 대화 요청이 긴 에이전트 작업에 밀리거나 특정 테넌트가 GPU를 독점합니다. llm-d 1.0의 flow control은 우선순위와 공정성을 함께 고려해, 중요한 요청에 지연 예산을 우선 배정하고 낮은 우선순위 작업은 여유 용량에서 실행하거나 포화 시 보류할 수 있게 합니다.

여기서 중요한 것은 QoS 정책을 애플리케이션 요구와 연결하는 일입니다. “프리미엄 고객 우선”만 선언하면 공정성 없는 선점 정책이 됩니다. 테넌트별 동시 요청 수, 토큰 예산, 최대 대기시간, 초과 시 재시도 규칙을 수치로 정하고, 우선순위가 높은 요청의 P95 TTFT와 낮은 우선순위 작업의 완료율을 함께 모니터링해야 합니다. 우선순위를 올리는 것만으로 GPU가 늘어나지는 않으므로, 포화 상태에서는 일부 비긴급 작업을 큐에 보관하거나 거부하는 정책도 필요합니다.

## 7. “오픈소스라서 자동으로 저렴하다”는 결론은 위험하다

IBM·Red Hat은 3,000개의 코딩 에이전트를 544개의 NVIDIA H100에서 운영한 사례와 약 98%의 프리픽스 캐시 적중률, 토큰 100만 개당 약 0.11달러라는 결과를 소개했습니다. IBM은 같은 오픈 모델을 독점 API로 제공하는 구성과 비교해 5~10배 낮은 비용을 시연했다고 설명합니다. 이 사례는 반복되는 긴 문맥에서 캐시 재사용이 비용 구조를 바꿀 수 있음을 보여주는 좋은 신호입니다.

하지만 자체 운영 비용에는 다음 항목이 포함됩니다.

- GPU 임대·감가상각과 전력
- Kubernetes·네트워크·스토리지 운영 인력
- 모델 가중치와 컨테이너 이미지의 저장·배포
- 관찰성, 보안 패치, 장애 대응
- 유휴 용량과 지역별 예비 용량
- 프리필·디코드 분리에 필요한 노드 간 통신

따라서 API 사용량이 작거나 요청이 짧고 불규칙하면 관리형 API가 더 쌀 수 있습니다. llm-d의 경제성은 “오픈소스” 자체보다 **충분히 큰 반복 문맥과 일정한 트래픽을 기존 GPU 자원에서 얼마나 재사용하는가**에 달려 있습니다. 비용 비교는 토큰당 가격이 아니라 GPU 시간, 캐시 적중률, P95 지연, 운영 인건비를 포함한 총소유비용으로 해야 합니다.

## 8. 어떤 조직에 적합하고, 어디에는 과한가

llm-d 1.0이 특히 잘 맞는 경우는 다음과 같습니다.

- 여러 팀과 테넌트가 하나의 GPU 클러스터를 공유하는 조직
- 에이전트·코딩 도우미처럼 동일 문맥을 여러 턴 재사용하는 서비스
- vLLM과 SGLang, GPU와 TPU처럼 엔진·가속기가 혼합된 환경
- 프리필·디코드 자원을 독립적으로 확장해야 하는 긴 문맥·대형 MoE 서비스
- 모델 서버를 무중단으로 업그레이드해야 하는 내부 플랫폼

반대로 다음 조건이라면 먼저 단순한 단일 엔진 구성을 검토하는 편이 좋습니다.

- 단일 모델, 단일 GPU 노드, 소수의 사용자
- 대부분의 요청이 짧고 프리픽스 공유가 낮은 서비스
- Kubernetes 운영 경험과 GPU 관찰성 체계가 아직 없는 팀
- 캐시 이동을 위한 네트워크·스토리지가 준비되지 않은 환경

llm-d는 vLLM이나 SGLang을 대체하는 애플리케이션 프레임워크가 아닙니다. 기존 엔진으로도 한 노드 서비스가 충분하다면 llm-d 계층을 추가할 이유가 없습니다. 규모가 커질 때 얻는 라우팅·QoS·운영 이점과, 그에 따라 늘어나는 제어면 복잡성을 비교해야 합니다.

## 9. 도입 단계별 체크리스트

### 1단계: 기준선 만들기

먼저 현재 모델 서버에서 다음 지표를 수집합니다.

- TTFT 중앙값·P95
- 초당 입력·출력 토큰
- GPU 메모리와 KV 캐시 사용량
- 프리픽스 캐시 적중률
- 테넌트별 큐 대기시간
- 모델 재시작·롤링 배포 시간
- GPU 시간당 비용과 유휴율

같은 모델과 하드웨어로 라운드로빈 기준선을 남겨야 llm-d의 효과를 분리할 수 있습니다.

### 2단계: 라우팅만 추가하기

처음부터 프리필·디코드 분리를 켜지 말고, 기존 vLLM 복제본 앞에 Endpoint Picker와 프리픽스 인식 라우팅을 붙입니다. 캐시 적중률과 TTFT가 실제로 좋아지는지 확인하고, 라우터 장애 시 트래픽이 어떻게 우회되는지 시험합니다.

### 3단계: 캐시 오프로딩과 QoS 검증

GPU HBM이 부족한 긴 문맥 워크로드에서 CPU 메모리 오프로딩을 먼저 시험합니다. 그 다음 낮은 우선순위 배치와 대화형 요청을 동시에 보내 flow control이 SLO를 지키는지 확인합니다. 저장소를 추가할 때는 캐시 읽기 지연과 장애 시 캐시 손실을 측정합니다.

### 4단계: 프리필·디코드 분리

두 풀의 모델·토크나이저·KV 형식이 일치하는지 고정하고, DisaggregatedSet으로 롤링 업데이트를 시험합니다. 프리필 풀 또는 디코드 풀이 먼저 고갈되는 상황을 인위적으로 만들어 자동 확장과 재시도 동작을 확인합니다.

### 5단계: 운영 자동화

KEDA/HPA 같은 추론 지표 기반 오토스케일링, Prometheus·OpenTelemetry 관찰성, 이미지 서명과 GitOps 배포를 연결합니다. 장애 시 라우터 hot standby가 전환되는지, 이전 버전으로 롤백할 때 캐시가 안전하게 폐기되는지 runbook을 작성합니다.

## 10. 벤더 벤치마크를 읽는 법

이번 발표에는 인상적인 수치가 많습니다. Google은 특정 TPU 실험에서 TTFT 85% 이상 개선과 처리량 2.4배를, IBM은 3,000개 에이전트와 98% 캐시 적중률을, Google Cloud의 GKE 설명은 17,000노드·3개 클러스터에서 2.9배 처리량과 99.9% 성공률을 제시합니다.

이 숫자를 검증할 때는 최소한 다음 질문을 던져야 합니다.

1. 사용한 모델·양자화·토크나이저 버전은 무엇인가?
2. 요청의 공통 접두사와 평균 문맥 길이는 얼마인가?
3. 캐시가 이미 예열된 상태인가, 콜드 스타트가 포함됐는가?
4. 비교 대상이 일반 Kubernetes Service인지, 캐시 인식 라우터인지?
5. TTFT 개선과 전체 비용·P95 지연이 같은 방향으로 움직였는가?
6. 장애·롤링 업데이트·테넌트 경쟁 중에도 같은 결과가 나오는가?
7. 네트워크·스토리지·운영 인건비를 비용 계산에 넣었는가?

llm-d 프로젝트는 재현 가능한 레시피와 Prism 대시보드를 제공한다고 안내합니다. 도입팀은 공개 설정을 그대로 따라 하는 데서 멈추지 말고, 자신의 프롬프트 분포·동시성·테넌트 비율을 포함한 부하 테스트를 별도로 만들어야 합니다. 성능 수치 하나보다 **어떤 요청이 캐시를 재사용했고, 어떤 요청이 큐에서 기다렸는지**를 추적하는 것이 중요합니다.

## 교육과 실무에서 해볼 수 있는 실험

실제 개인정보 대신 공개 모델과 합성 문서를 사용해 다음 실습을 구성할 수 있습니다.

1. vLLM 복제본 2~3개를 Kubernetes에 배포하고 라운드로빈 기준선을 측정합니다.
2. 동일한 긴 시스템 프롬프트를 여러 턴 보내 프리픽스 캐시 적중률을 기록합니다.
3. 캐시 인식 라우팅을 켠 뒤 세션이 같은 복제본에 머무는지 확인합니다.
4. GPU 메모리 사용량을 높여 CPU 오프로딩을 유도하고 TTFT와 전송량을 비교합니다.
5. 프리필·디코드 풀을 분리한 뒤 긴 문서와 짧은 대화 요청을 동시에 발생시킵니다.
6. 우선순위가 다른 테넌트를 만들어 flow control이 P95 지연과 공정성을 어떻게 바꾸는지 측정합니다.
7. 라우터 한 대를 중단하고 hot standby 전환 시간과 진행 중 요청의 결과를 확인합니다.
8. 프리필·디코드 이미지를 서로 다른 버전으로 배포해 호환성 검사가 트래픽을 막는지 검증합니다.
9. Prometheus·OpenTelemetry로 라우팅 결정, 캐시 적중·퇴거, 큐 대기, 토큰 지연을 하나의 트레이스로 연결합니다.
10. 마지막으로 GPU 비용·스토리지·운영시간을 포함해 관리형 API와 총비용을 비교합니다.

이 실험의 목표는 “llm-d를 설치했다”가 아닙니다. 어떤 문맥이 어디에 캐시되고, 어떤 정책으로 요청이 지연·보류·재분배되며, 업그레이드 중 어떤 상태가 사용자에게 노출되는지를 설명하는 것입니다.

## 한계와 결론

llm-d 1.0은 LLM 추론의 병목이 모델의 계산 속도만이 아니라 **문맥 재사용, 자원 경쟁, 배포 중 안정성**이라는 사실을 운영 계층에 반영한 릴리스입니다. vLLM·SGLang을 그대로 활용하면서 캐시 인식 라우팅, 계층형 KV 캐시, 프리필·디코드 분리, 멀티테넌트 QoS, 라우터 고가용성을 Kubernetes 방식으로 조합할 수 있습니다. 에이전트가 늘고 여러 GPU·클라우드·테넌트가 한 플랫폼을 공유하는 조직이라면 검토할 가치가 큽니다.

그러나 다음의 한계는 분명합니다.

- 캐시 인식은 공통 접두사가 있고 세션이 재사용될 때 효과가 큽니다.
- KV 오프로딩은 네트워크·스토리지 지연과 장애 모드를 새로 만듭니다.
- 프리필·디코드 분리는 독립 확장을 가능하게 하지만 두 풀의 호환성·용량·전송을 운영해야 합니다.
- QoS는 부족한 GPU 용량을 만들어내지 않으며, 어떤 요청을 보류·거부할지에 대한 제품 정책이 필요합니다.
- 벤더가 발표한 비용·성능 수치는 특정 워크로드의 결과이며, 작은 트래픽이나 짧은 요청에는 맞지 않을 수 있습니다.
- Kubernetes와 GPU 관찰성, 모델·이미지 공급망을 운영할 역량이 없는 팀에는 단일 모델 서버보다 과한 선택일 수 있습니다.

따라서 도입 순서는 “1.0을 설치하고 모든 기능을 켜기”가 아니라 다음과 같아야 합니다.

1. 현재 서비스의 TTFT·캐시 적중률·테넌트별 지연을 기준선으로 남깁니다.
2. 프리픽스 인식 라우팅 하나만 추가해 재사용 효과를 확인합니다.
3. GPU 메모리 압박이 실제로 있을 때 KV 오프로딩을 도입합니다.
4. 트래픽 우선순위와 실패 시 보류·거부 정책을 먼저 합의합니다.
5. 프리필·디코드 분리와 무중단 업데이트를 작은 풀에서 검증합니다.
6. 운영비·관찰성·장애 대응까지 포함한 총소유비용을 비교합니다.

llm-d 1.0의 가장 큰 변화는 더 빠른 모델 서버 하나가 아니라, **추론을 다른 클라우드 서비스처럼 운영할 수 있는 공통 제어면**을 제시했다는 데 있습니다. 에이전트가 반복해서 같은 문맥을 읽고, 여러 사용자가 한 GPU 풀을 공유하며, 모델과 가속기가 계속 바뀌는 환경에서는 이 제어면이 곧 비용과 사용자 경험을 좌우합니다. 다만 그 가치는 규모와 운영 성숙도가 있을 때 나타납니다. 먼저 우리 트래픽의 문맥 재사용과 테넌트 경쟁을 측정하고, 그 결과가 분산 추론의 복잡성을 정당화할 때 단계적으로 도입하는 것이 가장 안전합니다.
