AI 에이전트를 운영 환경에 붙일 때 가장 어려운 지점은 모델이 문장을 잘 만드는가가 아닙니다. 환불·계정 잠금 해제·장애 조치처럼 **정해진 순서와 승인 규칙이 있는 업무를 모델이 임의로 건너뛰지 못하게 하는가**가 더 어렵습니다. 프롬프트에 “항상 자격 확인 후 관리자 승인을 받고 크레딧을 지급하라”고 적어도, 실제 실행 순서를 모델의 다음 토큰에 맡기는 순간 재시도·타임아웃·보상 처리·감사가 불안정해집니다.

AWS는 2026년 10월 29일 기존 **AWS Step Functions Standard·Express 워크플로를 Amazon Bedrock AgentCore Gateway를 통해 AI 에이전트의 도구로 사용할 수 있다**고 발표했습니다. 에이전트는 언제 어떤 입력으로 워크플로를 시작할지 결정하지만, 워크플로 안의 단계는 Step Functions가 정의된 순서대로 실행합니다. 하루 전인 10월 28일에는 AgentCore의 AWS Agent Registry가 런던·프랑크푸르트·오하이오·캐나다 중부 리전에 추가되어, MCP 서버·도구·에이전트·스킬을 승인 흐름이 있는 검색 가능한 카탈로그에 등록할 수 있게 됐습니다.

두 발표를 하나의 설계 문제로 묶으면 메시지는 분명합니다. **모델은 의도를 해석하고 적절한 업무를 고르되, 업무의 안전한 실행 절차는 상태 머신과 권한·승인 계층이 맡는다**는 것입니다. 이는 에이전트에 더 많은 자율성을 주는 발표처럼 보이지만, 실제로는 자율성의 경계를 코드와 운영 정책으로 다시 그리는 변화입니다.

> 이 글은 AWS 공식 What's New 발표와 AWS News Blog, Agent Registry 지역 확장 안내, 독립적인 AIATS SRE 분석을 교차 확인해 작성했습니다. 제공 리전·요금·지원 작업은 계정과 시점에 따라 달라질 수 있으므로 도입 전 최신 AWS 문서를 확인해야 합니다.

## 1. 이번 발표에서 실제로 바뀐 것

### 에이전트 도구가 “함수 호출”에서 “검증된 업무 흐름 호출”로 확장됐다

AWS의 10월 29일 발표는 Step Functions를 새로 만드는 기능이 아닙니다. 이미 운영 중인 Standard·Express 상태 머신을 AgentCore Gateway의 커넥터 대상에 노출하는 기능입니다. AgentCore Gateway는 에이전트와 도구를 MCP(Model Context Protocol) 방식으로 연결하고, 에이전트가 전달한 입력을 지정된 상태 머신 실행으로 넘깁니다.

AWS가 제시한 환불 예시는 구조를 잘 보여 줍니다. 고객지원 에이전트는 환불이 필요하다고 판단해 워크플로를 시작할 수 있지만, 자격 확인·관리자 승인·크레딧 지급의 순서는 상태 머신에 고정됩니다. 에이전트가 “승인 단계를 생략하자”고 다음 메시지를 생성해도 상태 머신 정의가 바뀌지 않는 한 실행 경로가 달라지지 않습니다.

또한 에이전트는 워크플로 실행을 조회할 수 있습니다. 운영 에이전트가 “밤새 어떤 주문 처리가 실패했는가”를 묻고, 실행 이력에서 실패한 상태를 찾아 담당자가 해당 단계부터 조사하게 만드는 시나리오입니다. 즉 시작 작업과 조회 작업을 함께 제공하되, 둘은 다른 위험도의 도구로 취급해야 합니다.

### Agent Registry는 도구를 찾는 검색창이 아니라 승인 경계다

10월 28일 AWS 발표에 따르면 Agent Registry는 네 개 리전에 추가되어 총 아홉 개 리전에서 사용할 수 있게 됐습니다. 조직은 MCP 서버·도구·에이전트·에이전트 스킬·사용자 정의 리소스를 등록하고, 승인 워크플로를 거친 뒤 사람과 에이전트가 하이브리드 검색·카탈로그 탐색·네이티브 MCP 엔드포인트로 발견하게 할 수 있습니다.

도구를 검색할 수 있다는 사실보다 중요한 것은 **누가 등록했고 누가 승인했으며 현재 어느 버전인지**가 카탈로그의 일부가 된다는 점입니다. 에이전트가 임의로 인터넷의 MCP 서버를 붙이는 구조에서는 설명 문자열만 보고 위험한 도구를 선택할 수 있습니다. Registry를 사용하면 허용된 도구의 소유자·데이터 분류·런북·검토 상태를 등록 단계에서 요구할 수 있습니다.

| 구성 요소 | 에이전트에게 보이는 역할 | 통제해야 할 값 |
| --- | --- | --- |
| AgentCore Gateway | MCP 기반 도구 연결·정책 집행 | 대상 도구, 인증, 호출 속도, 입력 스키마 |
| Step Functions | 다단계 업무의 결정적 실행 | 상태 순서, 재시도, 타임아웃, 보상 단계 |
| Agent Registry | 승인된 도구·에이전트 검색 | 소유자, 버전, 데이터 등급, 승인·만료일 |
| IAM 역할 | 게이트웨이·상태 머신의 실제 권한 | 시작 가능한 ARN, 접근 리소스, 조건 키 |
| 실행 이력·CloudTrail | 누가 무엇을 시작·변경했는지 증명 | trace ID, principal, 입력 요약, 결과 |

## 2. “에이전트가 결정하고 워크플로가 실행한다”는 분리

이 구조를 단순히 “LLM이 Step Functions를 호출한다”고 설명하면 핵심을 놓칩니다. 책임을 네 단계로 나누면 다음과 같습니다.

1. **의도 해석**: 에이전트가 사용자의 요청에서 목표와 필요한 업무를 추정한다.
2. **도구 선택**: Registry에서 승인된 도구를 찾고, Gateway가 제공한 스키마에 맞는 입력을 만든다.
3. **절차 실행**: Step Functions가 입력을 검증하고 상태를 정해진 순서대로 실행한다.
4. **결과 확인**: 에이전트가 실행 이력과 결과를 읽어 사용자에게 설명하되, 결과가 실제로 완료됐는지 별도 검증한다.

여기서 모델이 통제하는 부분은 1·2단계에 가깝고, 데이터 변경이 발생하는 3단계는 코드화된 상태 머신이 맡습니다. 이는 모델이 덜 똑똑해도 안전한 구조입니다. 모델이 애매한 요청을 해석하는 능력은 남겨 두되, 승인·지급·삭제·배포의 순서를 모델의 기억력에 의존하지 않기 때문입니다.

### 프롬프트 기반 절차와 상태 머신 기반 절차 비교

| 항목 | 프롬프트에 절차를 적는 방식 | Step Functions를 도구로 노출하는 방식 |
| --- | --- | --- |
| 순서 보장 | 모델의 계획과 재시도에 의존 | 상태 전이 정의로 고정 |
| 승인 | 모델이 승인 요청 문장을 생성 | 태스크 토큰·콜백 등 명시적 상태 |
| 타임아웃 | 런타임별 구현 차이 | 상태·작업별 타임아웃 설정 |
| 재시도 | 중복 실행 위험을 별도 설계 | 재시도·백오프·보상 단계를 정의 |
| 감사 | 대화와 도구 로그를 사후 해석 | 실행 이력·상태·입력으로 재현 |
| 변경 관리 | 프롬프트 버전과 모델 버전 | 워크플로 정의·배포 버전과 함께 관리 |

이 비교는 Step Functions가 모든 문제를 해결한다는 뜻이 아닙니다. 상태 머신이 정확한 절차를 실행해도 에이전트가 **잘못된 워크플로를 고르거나 잘못된 입력을 넣으면** 사고가 발생합니다. 따라서 경계는 “모델 대 코드”가 아니라 의도·입력·권한·절차의 네 구간에 걸쳐 있어야 합니다.

## 3. 운영 아키텍처: 도구를 하나의 업무 API처럼 다루기

에이전트에 노출하는 워크플로는 일반적인 내부 함수보다 더 엄격한 API 계약을 가져야 합니다. 이름과 설명만 보고 모델이 선택하기 때문입니다.

### 도구 설계 원칙

- **한 도구, 한 업무**: `run_anything` 대신 `refund_customer`, `collect_incident_evidence`처럼 결과와 책임이 분명한 이름을 사용한다.
- **입력 스키마 제한**: 자유 텍스트를 첫 상태에서 바로 SQL·셸·HTTP 요청으로 넘기지 않고, 허용된 enum·정규식·리소스 ID로 변환한다.
- **읽기와 쓰기 분리**: 실행 조회 도구와 실행 시작 도구를 별도 대상으로 등록한다.
- **멱등성 키 요구**: 에이전트 재시도나 네트워크 재전송이 같은 환불·배포를 두 번 만들지 않도록 요청 ID를 상태 머신에서 검증한다.
- **결과를 구조화**: 성공·대기·거부·부분 실패를 문자열 한 줄이 아니라 상태 코드와 다음 조치 필드로 반환한다.
- **위험도 표기**: 돈·고객 데이터·프로덕션 변경을 발생시키는 워크플로는 Registry 메타데이터에 높은 위험 등급과 승인 요건을 기록한다.

예를 들어 환불 도구의 입력을 `customer_id`, `order_id`, `amount`, `reason`, `idempotency_key`로 제한하면 에이전트가 “고객에게 적당히 보상해 줘”라는 문장을 바로 결제 API에 전달할 수 없습니다. 첫 상태에서 주문 상태·통화·한도·중복 요청을 검증한 뒤, 승인 대기 상태로 이동해야 합니다.

### Standard와 Express 선택

AWS는 두 종류의 기존 워크플로를 도구로 사용할 수 있다고 안내합니다. 짧고 대량인 자동화라면 Express가 적합할 수 있지만, 사람 승인·규제 증적·장시간 처리·상세한 실행 조사가 필요하다면 Standard를 우선 검토해야 합니다. AIATS의 독립 분석도 금융·고객 데이터·프로덕션 영향이 있는 작업에는 태스크 토큰 승인과 Standard 워크플로의 실행 이력을 고려하라고 권고합니다.

선택 기준은 지연 시간 하나가 아닙니다.

| 질문 | Standard를 우선 검토할 조건 | Express를 검토할 조건 |
| --- | --- | --- |
| 사람 승인 | 승인 대기·재개가 필요함 | 승인 없는 자동 처리 |
| 감사 | 개별 상태와 입력을 장기간 재현해야 함 | 집계 지표 중심 |
| 실행 시간 | 긴 작업·외부 시스템 대기 | 짧고 예측 가능한 작업 |
| 비용 모델 | 상태 전이 수와 감사 가치 비교 | 고빈도·단순 처리 비용 비교 |
| 실패 처리 | 보상 트랜잭션과 수동 복구 | 재시도 후 알림으로 충분 |

## 4. 권한 모델은 두 번 나눠야 한다

에이전트가 상태 머신을 시작할 수 있다는 권한과, 상태 머신의 각 단계가 실제 데이터·서비스를 변경할 수 있는 권한은 분리해야 합니다. Gateway 역할에 광범위한 `states:StartExecution`과 여러 리소스 권한을 한꺼번에 주면, 모델이 워크플로를 고르는 실수 하나가 조직 전체 변경으로 이어집니다.

### 게이트웨이 역할

- 이름이 지정된 상태 머신 ARN만 시작할 수 있게 한다.
- 실행 조회는 별도 역할·별도 도구로 분리한다.
- 입력에 테넌트·계정·환경을 나타내는 조건을 요구한다.
- 개발·스테이징·프로덕션의 도구 카탈로그를 나눈다.

### 상태 머신 역할

- 각 태스크가 필요한 리소스만 읽거나 쓰게 한다.
- 결제·고객 데이터·권한 변경 단계는 조건부 정책과 별도 승인으로 감싼다.
- 외부 API 호출의 목적지와 메서드를 제한한다.
- 비밀값은 입력 프롬프트가 아니라 Secrets Manager 등에서 런타임에 가져온다.

이중 분리가 되어야 “에이전트는 환불 업무를 시작할 수 있지만 고객 DB 전체를 읽을 수 없고, 환불 워크플로도 승인 전에는 크레딧을 지급할 수 없다”는 경계를 만들 수 있습니다.

## 5. Registry가 해결하는 문제와 해결하지 못하는 문제

Registry는 도구가 많아질 때 검색과 승인 상태를 관리하는 데 유용하지만, 등록됐다는 사실만으로 도구가 안전해지는 것은 아닙니다.

### 해결하는 문제

- 조직 안에 어떤 MCP 서버·에이전트·워크플로가 있는지 파악
- 소유자와 리뷰어가 없는 도구가 자동 발견되는 것을 방지
- 설명·태그·데이터 분류를 이용한 검색
- 승인된 버전과 만료된 버전의 구분
- 사람과 에이전트가 같은 카탈로그를 조회하도록 통합

### 별도 설계가 필요한 문제

- 워크플로 자체의 비즈니스 로직 오류
- 설명과 실제 동작이 다른 도구
- 입력 검증이 약한 상태 머신
- 등록 후 변경된 컨테이너·MCP 서버의 공급망 위험
- Registry에서 검색한 뒤 도구가 실제 호출되는 리전·네트워크 경계
- 모델이 여러 도구를 조합해 만든 새로운 위험 경로

특히 Agent Registry의 검색 결과를 모델 컨텍스트에 넣는 경우, 설명·태그·사용 예시도 비신뢰 입력으로 취급해야 합니다. 등록자가 악의적이거나 실수로 과도한 능력을 설명하면 모델이 고위험 도구를 우선 선택할 수 있습니다. 검색 결과에는 반드시 위험 등급·승인 상태·입력 스키마·허용 환경을 함께 포함하고, 런타임에서 Gateway가 다시 검증해야 합니다.

## 6. 관찰성과 비용을 함께 설계하기

에이전트가 Step Functions를 호출하면 기존 워크플로 운영 지표와 새로운 AI 호출 지표가 연결됩니다. 다음 ID를 하나의 trace로 묶는 것이 좋습니다.

- `conversation_id`: 사용자의 대화나 티켓
- `agent_run_id`: 에이전트의 한 작업 수명주기
- `tool_call_id`: Gateway에서 생성한 도구 호출
- `execution_arn`: Step Functions 실행 ARN
- `principal_id`: 실제 사용자·서비스 계정·역할
- `idempotency_key`: 재시도 중복을 막는 업무 키
- `approval_id`: 사람 승인과 승인 범위

이 연결이 있으면 “모델이 환불을 제안했다”에서 멈추지 않고 “어떤 사용자가 어떤 에이전트 버전으로 환불 워크플로를 시작했고, 어느 승인 단계에서 대기했으며, 어떤 상태에서 실패했는가”를 재현할 수 있습니다.

비용도 동일한 trace에서 관리해야 합니다. AWS는 Step Functions와 AgentCore Gateway에 표준 요금이 적용된다고 안내합니다. Standard 워크플로의 상태 전이와 Gateway 호출이 에이전트 재시도로 반복되면, 모델 토큰 비용만 계산한 예산이 실제 청구액을 과소평가할 수 있습니다.

권장 알림은 다음과 같습니다.

| 알림 | 목적 |
| --- | --- |
| 동일 `idempotency_key` 재시작 | 중복 환불·중복 배포 방지 |
| 사용자별 워크플로 시작 급증 | 계정 탈취·무한 루프 탐지 |
| 승인 대기 시간 초과 | 사람 검토 병목과 자동 재시도 구분 |
| 읽기 대비 쓰기 호출 급증 | 에이전트 목표 변경·프롬프트 인젝션 탐지 |
| 실행 실패 후 즉시 재시작 반복 | 잘못된 입력 스키마와 모델 루프 발견 |
| 예상보다 큰 상태 전이 수 | 워크플로 분기·재시도 비용 점검 |

## 7. 실패 모드와 안전한 대응

### 잘못된 워크플로 선택

에이전트가 `unlock_account` 대신 `delete_account`를 선택하는 문제는 상태 머신이 해결하지 못합니다. 도구 설명을 명확히 하고, 위험도가 높은 도구는 Registry 검색 결과에서 사람 승인 후에만 발견되게 하며, Gateway에서 사용자 의도·대상 리소스·환경을 재검증해야 합니다.

### 잘못된 입력

에이전트가 주문 번호와 고객 번호를 바꾸거나 금액 단위를 잘못 넣을 수 있습니다. 첫 상태에서 원장·주문 시스템과 대조하고, 허용 한도 밖이면 실행하지 말고 사람에게 확인을 요청해야 합니다. 입력 검증 실패를 자연어 오류로만 반환하면 모델이 다른 값을 다시 시도할 수 있으므로 기계 판독 가능한 거부 사유를 함께 반환합니다.

### 부분 성공과 보상 처리

환불의 크레딧 지급은 성공했지만 알림 메일이 실패하는 것처럼 다단계 업무는 부분 성공이 정상적인 실패 형태입니다. 상태 머신에 보상 단계와 수동 조치 상태를 명시하고, 에이전트는 “완료” 대신 “지급 완료·알림 미전송”처럼 결과를 분해해 보고해야 합니다.

### Gateway·Registry 장애

Registry가 검색되지 않을 때 에이전트가 개인 MCP 서버로 우회하도록 허용하면 거버넌스가 무너집니다. 안전한 기본값은 승인된 도구를 찾지 못하면 실행하지 않고, 운영자가 수동으로 작업을 인계받는 것입니다. 반대로 단순 조회 업무는 읽기 전용 캐시나 제한된 대체 경로를 둘 수 있습니다.

### 재시도 폭주

모델이 타임아웃을 실패로 오인해 동일 워크플로를 반복 시작할 수 있습니다. 실행 시작 전 멱등성 키를 확인하고, 사용자·업무별 동시 실행 수와 시간당 예산을 제한합니다. 재시도는 모델이 결정하는 것이 아니라 Gateway와 상태 머신 정책이 결정해야 합니다.

## 8. 교육·실무에서 검증하는 실습 시나리오

이 발표를 실습으로 옮길 때는 실제 결제나 운영 DB를 연결하지 않고 합성 리소스를 사용합니다.

1. 테스트 계정 잠금 해제, 환불, 증거 수집 중 하나를 작은 Step Functions 상태 머신으로 만든다.
2. 첫 상태에서 JSON Schema와 멱등성 키를 검증한다.
3. 승인 전에는 읽기만 허용하고, 승인 후에만 쓰기 태스크를 실행한다.
4. 해당 상태 머신을 AgentCore Gateway의 단일 도구로 노출한다.
5. Registry에 소유자·위험 등급·데이터 분류·런북·만료일을 등록하고 승인 전후 검색 결과를 비교한다.
6. 에이전트에 모호한 요청, 중복 요청, 잘못된 ID, 타임아웃을 순서대로 입력한다.
7. 대화·도구 호출·실행 ARN·승인·비용 지표를 하나의 trace로 연결한다.
8. Kill Switch가 필요한 상황을 가정해 Gateway 차단 후 이미 실행된 상태와 큐를 점검한다.

학생이나 실무자는 모델 답변의 자연스러움보다 다음 질문에 답해야 합니다.

- 에이전트가 잘못된 업무를 선택했을 때 어느 계층에서 거부했는가?
- 중복 요청이 같은 업무를 두 번 실행하지 않았는가?
- 사람 승인이 필요한 상태가 모델의 설명만으로 통과되지 않았는가?
- 실패한 실행을 담당자가 같은 `execution_arn`으로 재현할 수 있는가?
- Registry에서 승인되지 않은 도구가 컨텍스트에 들어오지 않았는가?

## 9. 발표의 한계와 도입 전 확인 사항

첫째, 이번 기능은 AWS 서비스 조합에 강하게 의존합니다. 조직이 여러 클라우드와 자체 오케스트레이터를 함께 사용한다면, Step Functions를 도입하는 것만으로 전체 에이전트의 실행 경계가 통일되지 않습니다. 공통 trace 형식·도구 위험 등급·승인 정책을 먼저 정의하고, 클라우드별 어댑터를 두는 편이 현실적입니다.

둘째, “워크플로가 결정적이다”는 말은 상태 머신 내부가 올바르다는 전제 위에서만 성립합니다. 잘못된 조건식, 넓은 IAM 역할, 보상 단계 누락은 모델보다 오래된 전통적 장애를 그대로 남깁니다. 에이전트 연결 전에도 일반 애플리케이션처럼 계약 테스트·부하 테스트·장애 주입을 수행해야 합니다.

셋째, 지역 확장은 데이터 거버넌스를 자동으로 보장하지 않습니다. Registry에서 어떤 메타데이터와 검색 입력이 어느 리전에서 처리되는지, Gateway·모델·외부 API가 어디로 트래픽을 보내는지 계약과 문서로 확인해야 합니다. 특히 고객 데이터가 들어가는 도구는 “Registry가 런던에 있다”는 사실만으로 영국 내 처리라고 단정하면 안 됩니다.

넷째, 비용과 지연이 늘 수 있습니다. 모델 호출·Gateway·상태 전이·외부 승인 대기가 한 작업에 결합되기 때문입니다. 사용자가 단순 조회를 요청했는데 에이전트가 복잡한 워크플로를 선택하지 않도록 읽기 전용 도구와 실행 도구를 분리하고, 예산·시간·동시성 제한을 적용해야 합니다.

## 결론: 자율성은 모델에, 책임은 실행 계층에 남겨야 한다

AWS의 Step Functions·AgentCore Gateway·Agent Registry 조합은 에이전트가 프로덕션 업무를 수행하는 방법을 “모델이 모든 단계를 계획한다”에서 “모델은 승인된 업무를 선택하고 상태 머신이 절차를 실행한다”로 바꾸는 실용적인 패턴을 제시합니다. 기존 워크플로를 버리지 않고 도구로 노출할 수 있다는 점은 파일럿의 진입장벽을 낮추고, 실행 이력·IAM·승인·재시도라는 운영 자산을 재사용하게 합니다.

그러나 안전성은 자동으로 따라오지 않습니다. 도구 이름과 입력 스키마를 설계하고, Gateway와 상태 머신의 권한을 분리하고, Registry에서 소유자·검토·만료를 관리하고, 실패·중복·부분 성공을 관찰 가능한 상태로 만들어야 합니다. 에이전트의 자유로운 판단은 **어떤 업무를 할지**에 한정하고, **어떻게 실행할지**는 검증된 상태 머신과 사람 승인에 남겨 두는 것이 이번 발표에서 얻을 가장 중요한 설계 원칙입니다.
