AI 보안에서 가장 위험한 변화는 공격 도구가 더 복잡해졌다는 사실만이 아닙니다. 취약점 발견과 악용 사이의 시간이 짧아지면서, 방어팀이 “다음 정기 배포 때 수정하자”고 기다릴 수 있는 구간 자체가 줄어들고 있다는 점입니다. 코드 수정이 검토·테스트·배포를 거치는 동안에도 공격자는 애플리케이션과 API를 계속 탐색할 수 있습니다.

F5는 2026년 11월 5일 **Developing frontier AI defenses with F5 and Google Cloud**라는 글에서 이 문제에 대한 공동 방어 구상을 공개했습니다. F5의 주장은 프론티어 AI가 애플리케이션 코드와 인프라 설정에서 알려지지 않은 약점을 찾고, 공격 단계까지 빠르게 연결할 수 있으므로 방어도 실시간 평가와 행동 기반 차단으로 바뀌어야 한다는 것입니다. F5는 WAF, API 보안, 봇 관리, DDoS 완화 기능을 통합한 WAAP(Web App and API Protection)에 AI 기반 위험 점수와 행동 분석을 결합하고, 코드 수준의 정식 수정이 준비될 때까지 가상 패치로 런타임을 보호하는 흐름을 제시했습니다.

이 발표를 그대로 “AI가 알아서 해킹을 막는다”라고 해석하면 곤란합니다. F5의 64% 수치는 자사의 *State of Application Strategy* 조사에서 나온 벤더 조사 결과이며, Google Threat Intelligence Group(GTIG)이 최신 AI 모델을 사용한 실제 제로데이 악용 사례를 보았다는 내용도 F5 글에서 인용한 관찰입니다. 독립적인 효능 벤치마크나 모든 환경에서의 차단 성공률을 의미하지는 않습니다. 반면 Google Cloud와 Mandiant의 2026년 *AI risk and resilience* 보고서는 공격자가 단순한 프롬프트를 넘어 에이전트형 공격 오케스트레이션으로 이동하고 있으며, 에이전트가 API를 호출하고 운영 설정을 바꾸는 환경에서는 정적 경계만으로 충분하지 않다고 설명합니다.

두 자료를 함께 읽으면 실무적인 결론이 나옵니다. **AI가 취약점 발견 속도를 높일수록, 방어 시스템은 탐지·격리·가상 패치·영구 수정의 시간을 하나의 운영 루프로 관리해야 합니다.** 이 글에서는 F5의 발표를 기술적 구성요소로 분해하고, 어떤 신호를 어디에서 봐야 하는지, 가상 패치가 해결하지 못하는 문제는 무엇인지, 교육과 실무에서 어떻게 검증할 수 있는지를 정리합니다.

## 1. 11월 5일 발표에서 실제로 바뀐 관점

### 시그니처보다 먼저 행동을 본다

전통적인 WAF는 알려진 공격 문자열, CVE와 연결된 패턴, 위험한 메서드 조합을 규칙으로 차단합니다. 이 방식은 반복되는 공격을 빠르고 예측 가능하게 처리하지만, 아직 시그니처가 만들어지지 않은 변형이나 여러 요청을 이어 붙인 공격에는 빈틈이 생길 수 있습니다.

F5가 설명한 WAF for Distributed Cloud는 각 요청을 여러 신호로 평가해 위험 점수를 계산하고, 알려진 패턴이 없더라도 비정상적인 요청 흐름을 차단하는 방향입니다. 여기서 중요한 것은 AI 모델의 문장 생성 능력이 아니라 **런타임에서 관찰되는 요청의 맥락을 숫자와 정책으로 바꾸는 것**입니다. 예를 들어 한 번의 요청만 보면 정상적인 JSON이어도, 짧은 시간에 서로 다른 계정으로 동일한 토큰을 사용하거나, API 스키마와 맞지 않는 필드를 반복해서 바꾸거나, 오류 응답을 기준으로 입력을 조금씩 조정하는 패턴은 별도의 위험 신호가 될 수 있습니다.

### WAAP는 제품 묶음이 아니라 관찰 범위의 결합이다

F5가 말하는 WAAP는 다음 영역을 하나의 정책과 데이터 흐름으로 연결합니다.

| 영역 | 주로 보는 신호 | 잘하는 일 | 단독으로 해결하기 어려운 일 |
| --- | --- | --- | --- |
| WAF | URL, 메서드, 헤더, 본문, 응답 코드 | SQLi·XSS·페이로드 변형 차단, 입력 검증 | 내부 업무 규칙 오류, 이미 훼손된 데이터 복구 |
| API 보안 | OpenAPI 스키마, 호출 순서, 인증·인가, 객체 ID | 비정상 API 사용과 BOLA 계열 위험 탐지 | 문서에 없는 정당한 예외, 서비스 내부 권한 오남용 |
| 봇 관리 | 장치·세션·속도·행동 궤적 | 자동 계정 생성·스크래핑·크리덴셜 스터핑 완화 | 분산된 정상 자동화와 악성 자동화의 완전한 구분 |
| DDoS 완화 | 트래픽 규모, 출발지, 프로토콜, 비용 | 대량 트래픽 흡수·우회·속도 제한 | 낮은 빈도의 정교한 애플리케이션 공격 |

한 영역의 탐지 결과를 다른 영역의 정책에 전달할 수 있어야 결합의 가치가 생깁니다. API 스키마 위반을 한 번 일으킨 클라이언트가 동시에 비정상적인 로그인 시도를 반복한다면 봇 점수를 올리고, 공격이 의심되는 경로에는 WAF의 더 엄격한 입력 정책을 적용할 수 있습니다. 반대로 각 제품이 서로 다른 사용자·세션·요청 식별자를 사용하면 “통합”은 관리 콘솔만 하나일 뿐, 실제로는 분리된 사일로로 남습니다.

## 2. Google의 위협 보고서와 교차해서 읽기

F5 발표의 핵심 메시지는 공격 속도에 맞춰 방어 속도를 높이자는 것입니다. Google Cloud의 Mandiant 특별 보고서는 그 배경을 더 넓게 설명합니다. 2026년 보고서에 따르면 기업은 에이전트형 시스템을 배치해 API를 호출하고, 프로덕션 설정을 최적화하고, 하이브리드 클라우드의 텔레메트리를 분석하고 있습니다. 동시에 공격자는 단순한 챗봇 프롬프트를 넘어 여러 단계의 공격 작업을 자동화하는 방향으로 이동하고 있습니다.

이 변화는 애플리케이션 보안팀에 두 가지 부담을 줍니다.

1. **공격 대상이 코드만이 아니다.** 모델 연결부, 도구 호출, API 키, 프록시, 데이터 소스, 에이전트의 실행 권한이 함께 공격면이 됩니다.
2. **경계가 런타임으로 이동한다.** 배포 시점에 안전해 보였던 코드도 에이전트가 새로운 도구와 데이터를 결합하면 의도하지 않은 요청을 만들 수 있습니다.

따라서 WAAP를 도입하더라도 에이전트의 IAM, 도구 허용 목록, 데이터 분류, 프롬프트 인젝션 방어를 별도로 설계해야 합니다. WAF가 악성 HTTP 요청을 막아도, 정상적인 인증 토큰을 가진 에이전트가 허용된 API를 잘못된 순서로 호출하는 문제까지 자동으로 해결하지는 않습니다.

## 3. 가상 패치는 “영구 수정 전의 안전한 시간”이다

F5가 제시한 흐름은 Distributed Cloud Web App Scanning이 고위험 문제를 찾으면 BIG-IP Advanced WAF에서 해당 악용 동작을 차단하고, 동시에 Google Cloud의 AI 기반 코드 수정 도구가 근본 원인을 고치는 구조입니다. 가상 패치는 코드와 런타임 사이에 놓이는 임시 방어막입니다.

가상 패치가 할 수 있는 일은 비교적 구체적입니다.

- 특정 URL·메서드·파라미터에서 위험한 입력 형태를 거부한다.
- 요청 본문과 헤더에 대한 길이·형식·허용 문자 범위를 줄인다.
- 알려진 우회 변형을 정규화한 뒤 동일한 정책으로 평가한다.
- 공격이 집중되는 엔드포인트의 속도와 동시성을 제한한다.
- 정상 트래픽의 표본을 유지하면서 의심 요청을 격리·관찰한다.

하지만 가상 패치는 데이터베이스에 이미 잘못 기록된 값을 복구하지 않습니다. 또한 권한이 있는 사용자가 정상적인 API를 잘못된 업무 순서로 호출하는 비즈니스 로직 취약점, 탈취된 자격증명을 이용한 저속 공격, 내부 서비스 사이의 신뢰 오용을 완전히 해결하지도 못합니다. 따라서 “차단 규칙이 생겼으니 취약점이 해결됐다”가 아니라, **정식 코드 수정이 배포될 때까지 위험을 제한했다**고 표현하는 편이 정확합니다.

### 가상 패치 운영 상태를 명시하라

가상 패치를 무기한 남겨 두면 예외 규칙이 누적되어 나중에 무엇이 중요한지 알 수 없게 됩니다. 각 규칙에 다음 메타데이터를 함께 보관하는 것이 좋습니다.

| 필드 | 예시 | 목적 |
| --- | --- | --- |
| 취약점 ID | 내부 티켓·CVE·스캐너 식별자 | 코드 수정과 연결 |
| 적용 범위 | 서비스·리전·경로·메서드 | 과도한 전역 차단 방지 |
| 근거 | 재현 요청, 로그, 테스트 케이스 | 왜 필요한지 설명 |
| 시작·만료 시각 | 2026-11-09 06:00 / 2026-11-16 06:00 | 기술 부채 방지 |
| 예외 승인자 | 서비스 오너·보안 담당자 | 책임과 감사 |
| 영구 수정 상태 | 개발·검증·배포 완료 | 제거 조건 결정 |
| 우회 관찰 | 차단 후 변형 시도 수 | 정책 효과와 공격 변화 측정 |

특히 만료 시각이 중요합니다. 만료 전 영구 수정이 끝나지 않았다면 자동 연장이 아니라 재평가 티켓을 생성하고, 영향도와 오탐률을 다시 검토해야 합니다.

## 4. AI가 생성한 방어 규칙의 검증 루프

AI가 취약한 코드와 공격 페이로드를 빠르게 분석할 수 있다면, 방어 규칙 생성도 빨라질 수 있습니다. 그러나 생성된 정규식이나 입력 제약을 즉시 프로덕션에 적용하는 것은 위험합니다. 정상 사용자의 특이한 입력을 차단하거나, 공격자가 규칙의 빈틈을 찾아 다른 표현으로 우회할 수 있기 때문입니다.

권장되는 검증 루프는 다음과 같습니다.

1. **관찰 모드**: 제안된 규칙을 차단하지 않고 정상·의심 요청에 어떤 영향을 주는지 기록한다.
2. **재현 테스트**: 원래 취약점을 재현하는 테스트와 정상 업무의 계약 테스트를 함께 실행한다.
3. **범위 축소**: 전체 호스트가 아니라 취약 경로·메서드·테넌트부터 적용한다.
4. **카나리 차단**: 트래픽의 일부 또는 테스트 계정에서 차단을 시작한다.
5. **우회 시험**: 인코딩, 대소문자, 중첩 JSON, 압축, 다른 헤더 등 변형을 자동으로 검증한다.
6. **승인·배포**: 담당자가 근거와 테스트 결과를 확인한 뒤 적용한다.
7. **회귀 관찰**: 오탐률, 오류 코드, 전환율, 공격 재시도와 서비스 지연을 모니터링한다.

이 루프는 보안팀이 모든 규칙을 손으로 작성하자는 뜻이 아닙니다. AI는 후보 규칙과 테스트 케이스를 빠르게 제안하고, 사람과 자동화된 계약 테스트는 그 규칙이 실제 서비스의 의미를 깨뜨리지 않는지 확인하는 역할을 맡습니다.

## 5. API와 에이전트 환경에서 달라지는 위험

일반 웹 페이지보다 API와 에이전트 도구는 가상 패치의 설계가 더 어렵습니다. API는 사람이 보는 화면이 아니라 프로그램이 읽는 계약이므로, 작은 스키마 변화도 클라이언트 장애로 이어질 수 있습니다. 에이전트는 같은 API를 여러 단계로 호출하면서 응답을 다음 입력으로 재사용하므로, 한 번의 비정상 응답이 장시간 루프를 만들 수 있습니다.

다음 경계를 명시해야 합니다.

- **스키마 경계**: 필수 필드·타입·열거값·최대 배열 길이를 검증한다.
- **객체 권한 경계**: 인증된 사용자와 요청의 객체 소유권을 매번 대조한다.
- **순서 경계**: 조회·검증·승인·쓰기의 호출 순서를 서버에서 확인한다.
- **도구 경계**: 에이전트가 호출할 수 있는 API와 메서드를 최소 권한으로 제한한다.
- **출력 경계**: 오류 응답에 내부 경로·비밀값·디버그 정보를 넣지 않는다.
- **비용 경계**: 에이전트별 호출량·동시성·재시도 예산을 제한한다.

WAAP는 요청을 볼 수 있는 좋은 위치에 있지만, 에이전트의 업무 맥락을 항상 알 수 있는 것은 아닙니다. 따라서 게이트웨이, API 서버, 워크플로 엔진, 데이터 계층에서 각각 검증해야 하며, “가장 앞단의 WAF가 막아 주겠지”라는 단일 방어선 가정은 피해야 합니다.

## 6. 운영팀이 측정해야 할 지표

AI 기반 방어의 가치는 “탐지 건수” 하나로 평가하기 어렵습니다. 다음 지표를 한 사건의 시간선으로 연결해야 합니다.

| 지표 | 정의 | 질문 |
| --- | --- | --- |
| 취약점 발견 시간 | 스캐너·연구자·공격 징후가 처음 기록된 시각 | 얼마나 빨리 알았는가? |
| 가상 패치 시간 | 발견부터 차단 정책이 적용된 시각까지 | 정식 수정 전 위험 구간은 몇 분이었나? |
| 영구 수정 시간 | 발견부터 코드 배포 완료까지 | 임시 방어가 얼마나 오래 남았나? |
| 오탐률 | 정상 요청 중 차단된 비율 | 서비스 품질을 얼마나 훼손했나? |
| 우회 시도율 | 변형 공격 중 탐지되지 않은 비율 | 규칙이 어떤 형태로 뚫렸나? |
| 만료 부채 | 만료일이 지났지만 제거되지 않은 가상 패치 수 | 임시 조치가 상시 규칙이 되었나? |
| 재현 가능성 | 사건을 동일 trace·요청으로 다시 분석할 수 있는 정도 | 감사와 사후 학습이 가능한가? |

이 지표는 보안팀만 보지 말고 개발·SRE·제품팀과 공유해야 합니다. 예를 들어 가상 패치 시간을 줄였지만 오탐으로 결제 실패가 증가했다면 성공으로 볼 수 없습니다. 반대로 가상 패치가 며칠 유지되더라도 영구 수정이 진행 중이고 우회 시도가 감소했다면, 그 상태를 명확한 만료 계획과 함께 관리할 수 있습니다.

## 7. 교육과 실무에서 검증하는 실습

실제 서비스나 고객 데이터를 연결하지 않고도 이 구조를 검증할 수 있습니다.

1. 의도적으로 취약한 테스트 API를 만든다. 예: 객체 ID 검증 누락, 과도한 JSON 배열, 느린 검색 엔드포인트.
2. OpenAPI 스키마와 정상 업무의 계약 테스트를 준비한다.
3. 자동화된 공격 생성기로 여러 변형 요청을 만들고, 기본 WAF와 행동 기반 규칙의 차이를 기록한다.
4. AI가 제안한 가상 패치를 관찰 모드에 배치한다.
5. 정상 트래픽의 경계 사례를 재생한 뒤 카나리 차단을 수행한다.
6. 인코딩·대소문자·중첩 구조·저속 재시도로 우회 시험을 한다.
7. 규칙을 제거하고 영구 코드 수정이 같은 공격을 막는지 확인한다.
8. 요청 ID, 사용자·세션, 정책 버전, 배포 버전을 하나의 사건 기록으로 연결한다.

학습의 목표는 “AI가 만든 규칙이 정답을 맞혔는가”가 아닙니다. 어느 계층에서 어떤 증거로 차단했는지, 오탐이 생겼을 때 어떻게 되돌리는지, 가상 패치가 언제 폐기되는지를 설명할 수 있어야 합니다.

## 8. 이번 발표의 한계와 도입 전 체크리스트

첫째, F5 발표는 벤더의 제품·서비스 조합을 소개하는 글입니다. 위험 점수와 행동 기반 탐지가 특정 산업·트래픽·암호화 구성에서 어느 정도의 재현율과 오탐률을 보이는지는 별도 검증이 필요합니다. “시그니처가 없어도 차단한다”는 설명을 모든 제로데이의 탐지 보장으로 확대해서는 안 됩니다.

둘째, F5가 인용한 GTIG의 제로데이 관찰은 공격 흐름이 바뀌고 있음을 보여 주는 신호이지, 모든 공격자가 동일한 능력을 사용한다는 통계는 아닙니다. 공격자 모델, 대상 서비스, 악용 성공 여부를 공개 자료만으로 일반화하지 말아야 합니다.

셋째, 가상 패치는 애플리케이션 전달 계층의 통제입니다. 호스트·컨테이너·데이터베이스·자격증명·비즈니스 로직의 근본 문제를 대신 고치지 않습니다. 보안팀은 임시 규칙과 코드 수정 티켓을 같은 식별자로 묶어야 합니다.

넷째, AI 방어 시스템 자체가 민감한 요청과 로그를 처리합니다. 프롬프트, 헤더, API 본문에 개인정보·토큰·영업 비밀이 들어갈 수 있으므로 수집 전 마스킹, 보존 기간, 모델 학습 사용 여부, 리전 간 전송을 확인해야 합니다.

도입 전에 다음 질문에 답할 수 있으면 좋습니다.

- 어떤 애플리케이션과 API가 WAAP의 보호 범위에 실제로 들어오는가?
- 요청·응답·세션·사용자·테넌트 ID를 하나의 추적 체계로 묶을 수 있는가?
- AI가 만든 규칙을 관찰·카나리·승인·롤백하는 절차가 있는가?
- 가상 패치마다 만료일과 영구 수정 담당자가 지정되는가?
- 에이전트와 서비스 계정의 호출 권한·비용·재시도 예산이 제한되는가?
- 차단 정책이 개인정보와 비밀값을 외부 분석 서비스로 보내지 않도록 설계됐는가?

## 결론: 방어의 핵심은 더 똑똑한 모델이 아니라 더 짧은 검증 루프다

프론티어 AI가 취약점 연구와 공격 자동화의 시간을 줄이면 방어팀은 “발견 후 다음 배포”라는 오래된 순서를 다시 생각해야 합니다. F5와 Google Cloud가 제시한 조합은 WAF·API 보안·봇·DDoS의 런타임 신호를 결합하고, 정식 코드 수정 전에는 가상 패치로 노출을 줄이며, 이후에는 영구 수정과 검증으로 임시 조치를 걷어내는 흐름을 보여 줍니다.

그러나 이 구조의 안전성은 제품 이름보다 운영 설계에 달려 있습니다. AI는 새로운 공격 패턴과 방어 규칙 후보를 빠르게 제안할 수 있지만, 범위 축소·계약 테스트·사람 승인·롤백·만료 관리는 여전히 시스템의 책임입니다. 특히 API와 에이전트 환경에서는 정상적인 인증 요청도 업무 순서와 권한을 벗어나면 위험할 수 있으므로, WAF 하나를 최종 방어선으로 삼아서는 안 됩니다.

실무자가 가져갈 원칙은 간단합니다. **AI를 방어에 쓰되, AI가 만든 방어를 다시 검증하는 루프를 설계하라.** 발견 시간, 가상 패치 시간, 영구 수정 시간, 오탐과 우회, 만료 부채를 함께 측정할 때 비로소 “빠른 AI 방어”가 운영 가능한 보안 역량으로 바뀝니다.
