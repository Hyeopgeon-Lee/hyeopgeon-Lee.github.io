LLM을 API로 호출해 답변을 받는 것과, 여러 단계를 거쳐 실제 업무를 끝내는 에이전트를 운영하는 것은 전혀 다른 문제입니다. 모델 호출만 구현하면 파일을 어디에 저장할지, 도구 호출을 몇 번 허용할지, 중단된 작업을 어떻게 재개할지, 실패한 외부 요청을 다시 보내도 안전한지를 개발자가 직접 결정해야 합니다. 이 주변 실행 계층을 최근에는 에이전트 하네스(agent harness)라고 부릅니다.

마이크로소프트와 GitHub는 2026년 10월 28일 이 실행 계층을 Microsoft Copilot harness라는 이름으로 확장했습니다. Foundry Agent Service에서 공개 프리뷰로 제공하며, Microsoft가 에이전트 루프와 샌드박스를 운영하고 사용자는 지식·절차·도구·모델을 정의하는 방식입니다. 같은 날 GitHub는 기존 GitHub Copilot SDK가 Microsoft Copilot SDK로 전환된다고 발표했고, VS Code와 Copilot 앱의 새 세션에는 Copilot harness가 기본으로 사용된다고 안내했습니다.

이번 글은 [Microsoft 공식 발표](https://blogs.microsoft.com/blog/2026/10/28/introducing-the-microsoft-copilot-harness-unlocking-the-potential-of-truly-multi-model-agentic-work/), [Microsoft Foundry Blog의 공개 프리뷰 문서](https://devblogs.microsoft.com/foundry/microsoft-copilot-harness-in-foundry/), [Microsoft Learn의 사용 안내](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/use-tools-skills-copilot-harness), [GitHub Changelog의 SDK 전환 공지](https://github.blog/changelog/2026-10-28-github-copilot-sdk-is-becoming-microsoft-copilot-sdk/), 그리고 독립 기술 매체의 공개 프리뷰 정리를 교차 확인했습니다. 핵심은 “더 똑똑한 모델 하나를 추가했다”가 아니라, 모델 선택과 실행 운영을 분리한 관리형 시스템이 등장했다는 점입니다.

## 1. 하네스는 모델과 무엇이 다른가

모델은 입력을 받아 다음 토큰이나 도구 호출을 추론합니다. 하지만 업무를 끝내려면 다음과 같은 상태와 제어가 필요합니다.

- 대화와 작업 파일을 어디에 보관할지
- 어떤 도구를 어떤 자격 증명으로 호출할지
- 여러 번의 모델·도구 호출을 어떤 순서로 묶을지
- 시간이 오래 걸리는 작업을 어떻게 중단하고 재개할지
- 하위 에이전트에 어떤 범위의 일을 위임할지
- 실패와 비용 한도를 어떻게 감시할지
- 사람이 승인해야 하는 경계를 어디에 둘지

이 기능을 애플리케이션마다 직접 만들면 모델을 교체할 때마다 오케스트레이션 코드와 안전장치를 다시 검증해야 합니다. Microsoft Copilot harness는 이 주변 기능을 하나의 실행 런타임으로 제공하고, 애플리케이션은 지시사항·스킬·도구·자료에 집중하도록 설계됐습니다.

다만 하네스가 모델을 대신하는 것은 아닙니다. 모델의 환각, 도구의 잘못된 응답, 권한 설정 오류를 자동으로 없애 주지 않습니다. 실행 계층을 표준화해도 업무 규칙과 검증 책임은 여전히 애플리케이션에 남습니다.

## 2. 10월 28일 공개 프리뷰의 네 가지 구성요소

Microsoft Foundry Blog는 이번 프리뷰를 네 가지 블록으로 설명합니다.

### 재사용 가능한 스킬

스킬은 지시문, 스크립트, 참고 자료를 하나의 절차 패키지로 묶습니다. 예를 들어 시장조사 에이전트의 스킬은 질문의 범위와 기간을 확인하고, 승인된 검색 도구로 근거를 모으고, 사실과 해석을 구분해 보고서를 작성하도록 정의할 수 있습니다.

스킬의 장점은 프롬프트를 복사해 붙이는 대신 버전 관리 가능한 업무 절차로 만든다는 점입니다. 반대로 스킬 파일 자체가 공급망이 될 수 있습니다. 외부 저장소에서 내려받은 스크립트가 비밀을 읽거나 승인되지 않은 URL로 데이터를 보낼 수 있으므로 코드 리뷰와 서명, 테스트가 필요합니다.

### 연결된 도구

Foundry 도구와 Model Context Protocol(MCP) 도구를 명시적으로 연결하고 인증·승인 정책을 설정합니다. MCP를 사용하면 검색, 사내 티켓, 데이터베이스, 배포 시스템을 같은 에이전트에 붙일 수 있지만, 연결이 곧 무제한 권한을 의미해서는 안 됩니다.

도구마다 읽기·쓰기·삭제를 분리한 자격 증명을 사용하고, 에이전트가 접근할 수 있는 테넌트·리전·데이터 기간을 제한해야 합니다. 자연어 지시가 SQL이나 API 호출로 바뀌는 순간에는 입력 검증, 속도 제한, 승인 큐가 필요합니다.

### 실행과 위임

하네스는 파일과 코드를 다루는 작업을 샌드박스에서 실행하고, bounded task를 하위 에이전트에 위임할 수 있습니다. 예를 들어 주 에이전트가 보고서 구조를 정한 뒤, 한 하위 에이전트는 자료 수집을 담당하고 다른 하위 에이전트는 수치를 검산하게 만들 수 있습니다.

위임의 핵심은 병렬화가 아니라 경계입니다. 하위 에이전트가 원본 고객 데이터나 운영 계정에 직접 쓰기 권한을 갖지 않도록 입력·출력 계약을 정해야 합니다. 주 에이전트가 결과를 그대로 합치지 않고 출처, 실패 상태, 검증 결과를 확인하는 단계도 필요합니다.

### 소스 관리되는 에이전트 정의

Foundry 포털에서 만들고 테스트할 수 있지만, 에이전트 정의와 스킬·지원 자료를 애플리케이션 코드와 함께 관리할 수 있습니다. 이 구조는 프롬프트 변경도 배포 변경이라는 사실을 팀의 개발 흐름에 포함시킵니다.

운영에서는 모델 이름만 기록해서는 재현이 어렵습니다. 에이전트 정의 버전, 스킬 커밋, 연결된 MCP 서버 버전, 정책 버전, 평가 데이터셋을 함께 기록해야 합니다.

## 3. 관리형 런타임의 구조

Copilot harness를 선택하면 Foundry가 에이전트 루프와 실행 환경을 관리합니다. 애플리케이션은 Responses API로 에이전트를 호출하고, Foundry 프로젝트의 역할·연결·정책이 도구 접근을 통제합니다.

작업 상태는 대화 기록과 별도로 관리됩니다. Microsoft Learn에 따르면 각 대화에는 파일과 실행 상태를 위한 워크스페이스가 있고, 샌드박스가 유휴 상태가 되거나 교체돼도 정상적인 범위의 워크스페이스 상태는 유지됩니다. 그러나 샌드박스는 고객이 관리하는 영구 저장소가 아닙니다. 중요한 결과물은 Foundry Files나 데이터베이스, 객체 저장소 같은 내구성 있는 서비스에 명시적으로 저장해야 합니다.

이 구분은 운영 설계에서 중요합니다.

| 구분 | 하네스가 제공하는 것 | 애플리케이션이 책임질 것 |
| --- | --- | --- |
| 모델 호출 | 모델·도구 단계의 실행 루프 | 모델 선택 기준과 품질 평가 |
| 파일·코드 | 격리된 샌드박스와 작업 공간 | 중요한 산출물의 영구 저장 |
| 도구 연결 | 지원 도구와 MCP 연결 경로 | 최소 권한, 승인, 데이터 범위 |
| 재개 | 관리형 런타임의 실행 제어 | 체크포인트와 중복 방지 |
| 스킬 | 재사용 가능한 절차 패키지 | 테스트·리뷰·버전 관리 |
| 위임 | 하위 에이전트 호출 구조 | 입력·출력 계약과 결과 검증 |

## 4. 프롬프트 에이전트와 호스티드 에이전트 중 무엇을 고를까

이번 프리뷰에서는 하네스의 선택이 에이전트 생성 시 고정됩니다. 기존 에이전트의 하네스를 나중에 바꿀 수 없고, 기존 에이전트는 변경되지 않습니다. 따라서 처음부터 작업의 경계를 정해야 합니다.

| 방식 | 적합한 상황 | 주요 부담 |
| --- | --- | --- |
| 일반 프롬프트 에이전트 | 지시사항과 제한된 도구만으로 충분한 단순 업무 | 파일·다단계 상태를 직접 설계 |
| Copilot harness 프롬프트 에이전트 | 스킬, 파일, MCP, 하위 에이전트, 관리형 실행이 필요한 복합 업무 | 프리뷰 제약과 플랫폼 종속성 |
| 호스티드 에이전트 | 자체 프레임워크·미들웨어·프로세스 모델이 차별화 요소인 경우 | 런타임과 복구 로직을 직접 운영 |

BYOM(Bring Your Own Model) 지원 여부도 확인해야 합니다. Microsoft의 광범위한 발표는 Copilot harness가 여러 모델 계열과 자체 키를 지원하는 방향을 설명하지만, Foundry 공개 프리뷰의 현재 문서는 Copilot harness에서 BYOM을 지원하지 않는다고 명시합니다. “멀티모델”이라는 표현을 곧바로 “모든 모델을 연결할 수 있음”으로 해석하면 안 됩니다. 실제로 사용할 지역, 모델, 도구 조합은 [지원 모델·지역·프리뷰 제한 문서](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/use-tools-skills-copilot-harness)를 확인해야 합니다.

## 5. 멀티모델의 이점과 재현성의 문제

Microsoft는 Copilot harness의 배경으로 특정 모델에 하네스를 고정하지 않고 작업에 맞는 모델을 선택하는 전략을 제시합니다. 공식 발표는 20개 이상의 프런티어 모델과 자체 키 사용을 언급하고, Rust로 런타임을 포팅해 세션 오버헤드와 첫 토큰 시간을 줄였다고 설명합니다.

하지만 모델을 자동 라우팅한다고 품질이 항상 좋아지는 것은 아닙니다.

1. 어떤 작업이 어떤 모델로 라우팅됐는지 기록하지 않으면 결과를 재현하기 어렵습니다.
2. 모델별 도구 호출 형식과 컨텍스트 길이가 달라 스킬이 한 모델에서만 잘 동작할 수 있습니다.
3. 여러 모델을 순차·병렬로 사용하면 지연시간과 토큰 비용이 늘어날 수 있습니다.
4. 모델 제공자의 정책과 가용성 변화가 에이전트의 행동에 영향을 줍니다.

따라서 평가 지표를 “최종 답변의 만족도” 하나로 두지 말고, 성공률·사람 검토율·도구 오류율·평균 지연·토큰 비용·중복 실행률을 함께 기록해야 합니다. 작업 유형별로 고정 모델을 사용하는 기준선과 자동 라우팅 결과를 비교하는 A/B 실험도 필요합니다.

## 6. 장시간 작업의 복구는 체크포인트 문제다

같은 날 발표된 호스티드 에이전트용 long-running resilience는 장시간 작업에서 중단을 감지하고 원래 입력으로 작업을 재시작하는 기능입니다. 그러나 재시작이 곧 정확한 재개를 뜻하지는 않습니다.

Microsoft 문서는 애플리케이션이 진행 단계와 중간 결과를 저장해야 하며, 다른 시스템을 갱신하는 작업은 중복 실행을 막아야 한다고 설명합니다. 예를 들어 보고서를 외부 문서 시스템에 생성하는 단계가 재시작되면 같은 보고서가 두 개 만들어질 수 있습니다.

실무에서는 다음 패턴을 권장합니다.

- 각 작업에 안정적인 작업 ID와 단계 ID를 부여합니다.
- 단계 완료 시 입력 해시, 출력 위치, 외부 시스템의 결과 ID를 저장합니다.
- 외부 쓰기 전에 결과 ID가 이미 존재하는지 확인합니다.
- 재시작된 작업은 마지막 성공 단계부터 시작하고, 확인되지 않은 단계는 멱등적으로 재시도합니다.
- 사람 승인이 필요한 부작용은 재시도 루프 밖의 승인 큐로 분리합니다.

대화 기록만 저장해 두면 충분하다는 생각은 위험합니다. 대화는 “무슨 말을 했는가”를 보존하지만, 파일 처리의 어느 단계까지 완료됐고 외부 API가 성공했는지는 보존하지 않습니다.

## 7. 보안 경계: MCP·샌드박스·에이전트 아이덴티티

Copilot harness는 실행 환경을 격리하지만, 격리는 권한 설계를 대체하지 않습니다.

### MCP 연결

MCP 서버는 도구 목록과 입력 스키마를 제공할 수 있습니다. 운영에서는 도구별로 다음을 확인해야 합니다.

- 실제로 호출되는 API와 저장 위치
- 읽기와 쓰기 권한의 분리
- 호출자 ID와 테넌트 경계
- 프롬프트에 포함될 수 있는 민감 데이터
- 재시도와 타임아웃 시 중복 요청 처리

“검색”이라는 이름의 도구가 내부적으로 파일을 내려받거나 외부에 데이터를 전송할 수 있으므로, 서버 소스와 네트워크 경로를 확인해야 합니다.

### 샌드박스

샌드박스에서 명령을 실행할 수 있어도 네트워크, 패키지 설치, 파일 업로드를 모두 허용할 이유는 없습니다. 허용 목록 기반의 명령과 아웃바운드 도메인을 적용하고, 작업 종료 후 임시 파일을 정리해야 합니다. 생성된 파일을 사용자에게 반환할 때는 악성 매크로, 경로 조작, 비밀 포함 여부를 별도로 검사합니다.

### 아이덴티티

Microsoft Learn은 에이전트의 instance identity에도 연결 도구를 호출하는 데 필요한 Foundry 역할을 부여해야 한다고 설명합니다. 개발자의 역할과 에이전트의 실행 역할을 같은 것으로 취급하지 말고, 에이전트에는 업무에 필요한 최소 권한만 부여해야 합니다. 특히 모델이 선택한 도구 호출은 사람의 로그인 세션과 분리해 감사 로그를 남겨야 합니다.

## 8. 비용과 프리뷰 조건

Foundry Blog에 따르면 Copilot harness 런타임 사용료는 2026년 12월 1일부터 소비량 기반으로 청구됩니다. 그 전까지 런타임 자체는 무료지만 모델 추론, 별도 과금 도구, 연결된 서비스 비용은 계속 발생합니다. 12월 1일부터 공개된 기준 가격은 샌드박스 컴퓨트가 vCPU-hour당 0.0994달러, 메모리가 GiB-hour당 0.0118달러이며 지역과 계약에 따라 달라질 수 있습니다.

이 가격은 모델 토큰 비용을 포함하지 않습니다. 장시간 작업에서 모델이 반복 호출되거나, 여러 하위 에이전트가 같은 자료를 다시 읽으면 런타임보다 추론 비용이 커질 수 있습니다. 다음과 같은 예산 가드를 먼저 두는 것이 좋습니다.

- 작업당 최대 실행 시간과 모델 호출 횟수
- 단계별 토큰·도구 예산
- 대용량 파일 처리 전 사전 추정
- 실패 재시도 횟수와 지수 백오프
- 사람 승인으로 전환하는 비용 임계치
- 개발·스테이징·운영 환경의 별도 한도

공개 프리뷰는 서비스 수준 계약이 없고 기능이 제한될 수 있습니다. 실제 운영에 투입하기 전에 같은 업무를 일반 프롬프트 에이전트와 호스티드 에이전트로도 실행해 복구 가능성, 비용, 품질을 비교해야 합니다.

## 9. 도입 체크리스트

Copilot harness를 선택하기 전에 다음 질문에 답해 보십시오.

### 업무 경계

- 한 번의 실행이 몇 분 또는 며칠까지 이어지는가?
- 중간 결과를 사람이 검토해야 하는가?
- 외부 시스템에 쓰기 작업이 포함되는가?
- 작업을 실패해도 재시도할 수 있는가?

### 실행 정의

- 스킬·도구·모델·정책이 모두 소스 관리되는가?
- 스킬 변경에 대한 회귀 테스트가 있는가?
- 사용한 모델과 도구 버전을 실행 기록에 남기는가?
- 하위 에이전트의 입력·출력 스키마가 고정되어 있는가?

### 권한과 데이터

- 에이전트 아이덴티티에 최소 권한을 부여했는가?
- MCP 도구가 접근하는 리소스 범위를 제한했는가?
- 샌드박스에서 네트워크와 패키지 설치를 제어하는가?
- 대화·파일·도구 결과의 보존 기간과 지역을 정했는가?

### 신뢰성과 비용

- 각 단계가 멱등적인가?
- 체크포인트와 외부 결과 ID를 저장하는가?
- 재시작 후 중복 보고서·중복 결제가 생기지 않는가?
- 성공률뿐 아니라 사람 개입률과 비용을 측정하는가?

## 10. 교육용 실험으로 검증하기

학생이나 개발자 교육에서는 외부 고객 데이터 없이도 하네스의 장단점을 재현할 수 있습니다.

1. 합성 문서 폴더를 만들고, 근거를 인용하는 연구 브리프 스킬을 정의합니다.
2. 웹 검색과 코드 인터프리터를 연결하되, 읽기 전용 데이터만 사용합니다.
3. 같은 질문을 일반 프롬프트 에이전트와 Copilot harness 에이전트에 보냅니다.
4. 자료 수집, 계산, 보고서 작성 단계를 별도 체크포인트로 저장합니다.
5. 보고서 저장 직전에 실행을 중단하고 다시 시작해 중복 파일이 생기는지 확인합니다.
6. 하위 에이전트에 계산을 위임하고, 원본 수치와 검산 결과를 비교합니다.
7. 모델을 바꿔도 스킬과 평가 기준이 유지되는지 측정합니다.
8. 호출 횟수, 지연시간, 토큰 비용, 사람 수정량을 표로 정리합니다.

실험의 성공 기준은 “그럴듯한 보고서가 나왔다”가 아닙니다. 어떤 모델과 도구가 사용됐는지, 재시작해도 부작용이 한 번만 발생했는지, 근거와 해석이 분리됐는지를 설명할 수 있어야 합니다.

## 한계와 결론

Microsoft Copilot harness 공개 프리뷰는 에이전트 개발의 초점을 모델 호출 코드에서 실행 운영으로 이동시킵니다. 재사용 스킬, MCP 도구, 파일·코드 샌드박스, 하위 에이전트 위임, 소스 관리되는 정의를 하나의 관리형 런타임으로 묶어 복합 작업의 초기 구현 부담을 줄입니다. GitHub Copilot SDK가 Microsoft Copilot SDK로 확장되는 방향과 VS Code의 기본 하네스 전환은 이 실행 계층을 여러 제품의 공통 기반으로 만들려는 신호입니다.

그러나 하네스가 곧 신뢰성을 보장하지는 않습니다.

- 공개 프리뷰에서는 기존 에이전트의 하네스를 변경할 수 없고, BYOM 등 지원 범위가 제한됩니다.
- 자동 멀티모델 라우팅은 비용·지연·재현성 평가가 없으면 운영 리스크가 됩니다.
- 장시간 작업의 재시작은 애플리케이션의 체크포인트와 멱등성 설계가 없으면 중복 부작용을 만듭니다.
- 샌드박스와 MCP 연결은 최소 권한·네트워크·데이터 보존 정책과 함께 운영해야 합니다.
- 12월부터 런타임 비용이 추가되므로 모델·도구·메모리 비용을 한 작업 단위로 계산해야 합니다.

권장 순서는 간단한 읽기 중심 업무에서 시작해 스킬과 도구의 경계를 검증하고, 체크포인트와 감사 로그를 붙인 뒤, 마지막에 외부 쓰기와 하위 에이전트 위임을 추가하는 것입니다. 모델을 바꾸지 않고도 실행 계층을 개선할 수 있다는 점은 분명한 장점입니다. 다만 플랫폼이 관리해 주는 부분과 애플리케이션이 책임져야 하는 부분을 먼저 나누어 문서화할 때, Copilot harness는 편리한 프리뷰를 넘어 장기 운영 가능한 에이전트 기반으로 발전할 수 있습니다.
